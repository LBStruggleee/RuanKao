一、面向对象设计原则

1.1 七大原则总览（必背）

在面向对象设计中，高内聚低耦合是总目标，下面这些原则是达到该目标的具体手段。软考常考的是每个原则的定义和用英文首字母缩写指认。

原则 英文 缩写 一句话定义 核心关键词
单一职责原则 Single Responsibility Principle SRP 一个类应该只有一个引起它变化的原因（只承担一个职责） 一个类/一个职责
开闭原则 Open-Closed Principle OCP 软件实体（类、模块、函数等）应该对扩展开放，对修改关闭 扩展开放、修改关闭
里氏替换原则 Liskov Substitution Principle LSP 所有引用基类的地方必须能透明地使用其子类对象，而程序行为不变 子类可替换父类
接口隔离原则 Interface Segregation Principle ISP 客户端不应该被迫依赖它不使用的方法；接口应小而专，不要建立庞大的接口 接口要小而专
依赖倒置原则 Dependency Inversion Principle DIP 高层模块不应依赖低层模块，二者都应依赖抽象；抽象不应依赖细节，细节应依赖抽象 面向接口编程
迪米特法则 Law of Demeter（最少知识原则） LoD 一个对象应该对其他对象保持最少的了解；只与"直接的朋友"通信 只跟直接朋友说话
合成复用原则 Composite Reuse Principle CRP 优先使用对象组合/聚合，而不是继承来达到复用的目的 组合优于继承

记忆口诀："单开里接依，迪合"（SRP、OCP、LSP、ISP、DIP、LoD、CRP）。前五个的首字母 S-O-L-I-D 正好组成 SOLID——这就是著名的"SOLID 原则"。

1.2 逐条举例说明

① 单一职责原则（SRP）

反面示例：一个"员工类"既负责考勤计算、又负责数据库持久化、还负责生成工资报表
  → 考勤规则变、数据库换、报表格式改，三类变化都会修改同一个类。

正面示例：拆分为 员工类(数据) + 考勤计算类 + 员工仓储类(持久化) + 工资报表类
  → 每个类只有一个"变化的原因"。

判据：问自己"这个类可能因为几个原因被修改？" 若超过一个，就违反 SRP。

② 开闭原则（OCP）

反面示例：计算运费的函数里写死 if(type=="普通")...else if(type=="加急")...，
  每新增一种配送方式就要改这个函数（修改既有代码）。

正面示例：定义接口 DeliveryStrategy，每种配送方式是一个实现类；
  新增方式只需新增类（扩展开放），原有代码一行不动（修改关闭）。

开闭原则是面向对象设计的"核心目标"，其余原则（LSP/DIP/ISP 等）都是实现开闭原则的手段。

③ 里氏替换原则（LSP）

经典反例：父类"矩形"有 setWidth/setHeight；子类"正方形"重写它们以保持宽高相等。
  若某处代码用 矩形类型 引用 并调用 setWidth(5)、setHeight(10)，期望面积=50，
  而正方形对象会让两边都变成 10（或 5），结果与预期不符 → 子类不能安全替换父类。

正确做法：正方形不应继承矩形，二者都继承自"形状"抽象类。

判据："子类对象能在任何使用父类的地方替换父类，且程序行为不变"。LSP 是继承合理性的检验——"is-a"关系不只是分类学上的归属，更要是行为上的兼容。

④ 接口隔离原则（ISP）

反面示例：一个"胖接口" Worker 包含 work()、eat()、sleep()。
  机器人实现 Worker 时被迫实现 eat()/sleep()（空方法），被迫依赖它不使用的方法。

正面示例：拆为 Workable{work()}、Eatable{eat()}、Sleepable{sleep()}；
  机器人只实现 Workable，人类实现三个。

判据：接口的成员越少越好，只放调用方真正需要的方法。

⑤ 依赖倒置原则（DIP）

反面示例：高层"订单服务"直接 new 低层"微信支付类" → 换支付宝就要改高层代码。

正面示例：定义接口 PaymentService；订单服务依赖该接口；
  微信/支付宝是实现类，由外部（如 Spring 容器/工厂）注入进来。
  高层与低层都依赖抽象 → 这就是"依赖倒置"。

依赖注入（DI）、控制反转（IoC）是依赖倒置原则的具体实现手段（常考辨析：原则是 DIP，手段是 DI/IoC）。

⑥ 迪米特法则（LoD）

反面示例：a.getB().getC().doSomething()  —— 对象 a 间接依赖了不认识的 c。

正面示例：b 提供 doSomethingAboutC()，a 只调用 b 的方法。

迪米特法则降低耦合，但过度使用会产生大量"转发方法"，增加系统复杂度——要权衡。

⑦ 合成复用原则（CRP）

继承（白箱复用）：子类直接获得父类实现，耦合度高，父类改变直接影响所有子类。
组合（黑箱复用）：把被复用对象作为成员，只依赖其外部接口，耦合度低。
→ 优先使用组合/聚合，继承只用于真正的 is-a 关系。

1.3 易混辨析（三组，必看）

① 开闭原则 vs 依赖倒置 vs 里氏替换——"谁是目标，谁是手段"？

问法 答案
"面向对象设计的核心目标/最基本的原则" 开闭原则（OCP）
"实现开闭原则的主要手段/方式" 依赖倒置（DIP）+ 里氏替换（LSP）+ 接口隔离（ISP）
"子类必须能替换父类" 里氏替换（LSP）
"高层不依赖低层，都依赖抽象" 依赖倒置（DIP）

关系链：LSP 保证子类替换安全 → DIP 让依赖指向抽象 → ISP 让抽象接口精简 → 共同支撑 OCP（不修改源码即可扩展）。

② 单一职责（SRP）vs 接口隔离（ISP）——"粒度控制的对象不同"

SRP 针对"类"：一个类不要承担多个职责（类的内部凝聚）。
ISP 针对"接口"：一个接口不要塞进客户用不到的方法（接口的外部暴露）。
两者常同时违反：一个"胖接口"往往也对应一个"多职责的类"。

③ 迪米特法则 vs 高内聚低耦合——"范围不同"

迪米特法则是"对象之间通信的最少知识原则"，属于设计层面的耦合控制；高内聚低耦合是"模块之间"的普适设计准则，范围更大，包含迪米特法则的思想。

二、耦合分级（必考核心）

2.1 什么是耦合

耦合（Coupling） 是软件结构中各模块之间相互连接程度的度量。耦合越低，模块独立性越强（这是设计的追求）。

⚠️ 重要前提：耦合与内聚讨论的是模块之间/内部的关系。判别耦合类型时，盯住"两个模块之间靠什么发生联系"。

2.2 七级耦合（从低到高，必背）

软考采用 Myers 的七级划分。从低耦合（好）到高耦合（坏）：

级别 名称 定义 例子 判断技巧
1 无直接耦合（非直接耦合） 两个模块之间没有直接联系，它们通过主模块或上层模块发生关系 模块 A、B 都只被主程序调用，互相不通信 看两者有无直接的数据/控制来往
2 数据耦合 两个模块间通过简单数据值（参数） 进行交互 avg = average(a, b) 传入两个整数 只传简单变量/常量，且只传需要的
3 标记耦合（特征耦合） 两个模块间传递的是数据结构（记录/数组/对象） update(emp) 传入整个员工记录，但只用其中 2 个字段 传了整个结构，接收方却只用一部分
4 控制耦合 一个模块向另一个模块传递控制信息（开关、标志、函数指针），控制对方的执行逻辑 process(data, "fast") 用字符串选择算法；回调函数 传的参数决定对方"怎么执行"，而不仅是"处理什么"
5 外部耦合 一组模块都访问同一外部环境（同一文件、同一设备、同一通信协议、同一全局外部接口） 多个模块都读写同一个配置文件 / 都操作同一台打印机 绑定的是程序之外的外部约定
6 公共耦合 一组模块都访问同一公共数据环境（全局变量、共享内存、公共数据区） 多个函数都读写全局变量 int g_count 绑定的是程序之内的公共数据区
7 内容耦合（最高） 一个模块直接访问另一个模块的内部数据或内部程序 模块 A 直接修改模块 B 的全局变量；非 goto 跳入 B 内部；汇编级直接访问 "越过对方接口，直接进入对方内部"

2.3 记忆口诀与判别流程

口诀："无直、数、标、控、外、公、内"（从低到高）。 判别三连问：

1) 两者有直接来往吗？
   无 ──→ 无直接耦合（最低）
   有 ↓
2) 来往的是"数据"还是"控制"？
   控制信息（开关/标志/回调）──→ 控制耦合
   数据 ↓
3) 传的是简单值还是数据结构？
   简单值且都有用 ──→ 数据耦合
   数据结构（对方只用一部分）──→ 标记耦合
4) 是否共享了什么？
   共享外部环境（文件/设备/协议）──→ 外部耦合
   共享公共数据区（全局变量）──→ 公共耦合
5) 是否直接进入对方内部？
   是 ──→ 内容耦合（最高，必须避免）

2.4 易错点辨析

① 标记耦合 vs 数据耦合——"传的是不是整个结构"

数据耦合：calc(x, y)          —— 传两个简单值
标记耦合：calc(employee)      —— 传整个员工对象，但只用 age 和 salary

⚠️ 判据不是"传了几个参数"，而是"被传数据的形式"：整体结构 → 标记；简单值 → 数据。标记耦合比数据耦合高一级，因为接收方依赖了它不需要的数据格式。

② 外部耦合 vs 公共耦合——"共享的东西在程序内还是程序外"

外部耦合：都遵循外部约定 —— 多个模块都读写同一个磁盘文件 / 都用同一个外部 SDK
公共耦合：都共享程序内数据 —— 多个模块都读写同一个全局变量 g_state

⚠️ 公共耦合的危险：一个模块修改全局变量，所有依赖它的模块行为都可能改变，且难以追踪。这是最该避免的耦合之一（仅次于内容耦合）。

③ 控制耦合的"隐蔽性"

process(record, true)   // true 表示"跳过校验" —— 这是控制耦合
process(record, mode)   // mode 决定算法分支       —— 这仍是控制耦合

只要参数影响被调用模块的执行路径，就是控制耦合，与参数类型无关（布尔、枚举、函数指针都算）。

三、内聚分级（必考核心）

3.1 什么是内聚

内聚（Cohesion） 是模块内部各元素（处理、数据）彼此结合的紧密程度的度量。内聚越高，模块独立性越强（这是设计的追求）。

⚠️ 判别内聚时，盯住"同一模块内的多个处理任务，是基于什么理由被放在一起的"。

3.2 七级内聚（从低到高，必背）

软考采用 Myers 的七级划分。从低内聚（坏）到高内聚（好）：

级别 名称 定义 例子 判断技巧
1 偶然内聚（巧合内聚） 模块内各任务之间没有任何实质联系，只是为图省事放在一起 一个"通用工具类"里塞了日期格式化、金额计算、发邮件，彼此无关 "删掉任何一个，其余不受影响"
2 逻辑内聚 模块内完成逻辑上相似的一类功能，由调用方传入控制参数选择执行哪一个 print(doc, "excel") / print(doc, "pdf")——一个模块处理所有导出格式 "多个功能相似 + 用开关参数选一个"
3 时间内聚 模块内各任务在同一时间段内执行（无逻辑关系，只是同时发生） init() 里同时做：读配置、建连接、清缓存、写日志 "同一时刻做一堆事，但互不相关"（初始化/收尾模块典型）
4 过程内聚 模块内各任务按特定顺序执行，前一个的输出不一定是后一个的输入 verify()：先校验格式 → 再查黑名单 → 再写审计日志（顺序固定但无数据流动） "有先后顺序，但无数据流传递"
5 通信内聚（信息内聚） 模块内各任务使用相同的输入数据或产生相同的输出数据 report()：用同一份销售数据生成报表 + 更新看板 + 推送提醒 "共用同一批数据，各干各的"
6 顺序内聚（序列内聚） 模块内一个任务的输出是另一个任务的输入，串成一条流水线 pipeline()：解析日志 → 过滤(输入=解析结果) → 聚合(输入=过滤结果) "前者的输出 = 后者的输入，串联"
7 功能内聚（最高） 模块内所有任务共同完成一个单一、明确的功能，缺一不可 calculateTax(income)：所有步骤都为算出税额这一件事 "一句话能说清这个模块干嘛，且少一步都不行"

3.3 记忆口诀

口诀："偶、逻、时、过、通、顺、功"（从低到高）。 类比记忆： - 偶然内聚 = 一群陌生人被关进同一节车厢（毫无关系） - 逻辑内聚 = 一类相似工具放一个抽屉（相似但各自独立） - 时间内聚 = 同时发生的事写进同一个闹钟（时间上是理由） - 过程内聚 = 按流程顺序走的流水线（有顺序，无数据流） - 通信内聚 = 围着同一张桌子（同一数据）各自吃饭 - 顺序内聚 = 接力赛（上一棒的结果交给下一棒） - 功能内聚 = 一个齿轮组（全部为一个功能服务，缺一不可）

3.4 易错点辨析（高频陷阱）

① 时间内聚 vs 过程内聚——"为什么在一起"

时间内聚：init() 里 读配置、建连接、清缓存 —— 只是"启动时都要做"，彼此无先后依赖
过程内聚：verify() 里 先格式校验、后查黑名单 —— 有固定的先后顺序（先快后慢，失败即终止）

⚠️ 区别在有无必然的先后关系：时间内聚的任务换个顺序也行；过程内聚的任务顺序有意义。

② 过程内聚 vs 顺序内聚——"有没有数据流"

过程内聚：A→B→C 但 A 的输出不给 B（顺序由流程/效率决定，如"先校验后落库"）
顺序内聚：A→B→C 且 A 的输出就是 B 的输入（数据在流水线上流动）

⚠️ 这是最高频的易错点。判据："前者输出是否是后者输入？" 是 → 顺序内聚；否 → 过程内聚。

③ 通信内聚 vs 顺序内聚——"数据是共享还是传递"

通信内聚：都用 inputData，各自产出不同结果（共享输入，并行无依赖）
顺序内聚：A 的输出成为 B 的输入（数据串联）

④ 逻辑内聚 vs 功能内聚

逻辑内聚：exportExcel()、exportPDF() 被合并成 export(type) —— 靠参数选择，内聚低
功能内聚：exportToPDF() 只做导出 PDF 一件事 —— 内聚高

3.5 内聚与耦合的关系

高内聚低耦合是同一枚硬币的两面：一个内聚高的模块，只对外暴露单一职责的精简接口，与其他模块的耦合自然就低。设计时从追求高内聚入手，低耦合往往随之而来。

四、软件测试方法总览

4.1 测试的分类维度

按是否运行程序：
  静态测试 —— 不实际运行被测软件：代码审查、走查、桌面检查、静态分析工具
  动态测试 —— 实际运行被测软件：构造输入、观察输出（本文的覆盖测试均属此类）

按是否关心内部结构：
  黑盒测试 —— 只看输入输出，不看内部代码（功能测试）
  白盒测试 —— 检查内部结构与执行路径（结构测试）
  灰盒测试 —— 介于两者之间（既关注输入输出，也关注部分内部实现）

按测试阶段（从小到大）：
  单元测试 → 集成测试 → 系统测试 → 验收测试

4.2 四个测试阶段（必考）

阶段 测试对象 主要方法 依据文档 典型关注
单元测试 单个模块/函数/类 白盒为主 详细设计说明书 模块内部逻辑、边界
集成测试 模块组装后的接口 白盒 + 黑盒 概要设计说明书 模块间接口、数据传递
系统测试 整个系统 黑盒为主 需求规格说明书 SRS 功能、性能、安全、恢复
验收测试 交付的系统 黑盒 用户需求/合同 是否满足用户需要（α/β 测试）

⚠️ 易错点：单元测试依据详细设计，集成测试依据概要设计，系统测试依据需求规格说明书。题目常把这三者打乱配对。

集成测试的两种策略：

策略 做法 需要的辅助模块 特点
自顶向下 从主模块开始，逐步接入下层 桩模块（Stub）：模拟被调用的下层模块 能早验证主控流程；底层未完成时可先测
自底向上 从底层模块开始，逐步组装 驱动模块（Driver）：模拟调用它的上层模块 底层先行；主控流程最后才测

口诀："自顶向下打桩，自底向上写驱动"（顶→桩、底→驱动）。

五、黑盒测试方法（功能测试）

黑盒测试把程序看作一个打不开的黑盒子，只依据需求规格说明书，不考虑内部实现。目标：发现"功能不对、接口错、数据错、性能不达标"等问题。

5.1 等价类划分法

核心思想：把所有可能的输入数据划分成若干"等价类"，每类中任取一个值作为代表——同一等价类中的任何一个输入，都能发现同样的问题。

划分原则： - 有效等价类：符合需求规则的输入（检验程序"该做的做了"）； - 无效等价类：违反需求规则的输入（检验程序"不该做的能挡住"）。

⚠️ 必考规则（最容易记错的一条）： 有效等价类可以合并覆盖（一个测试用例可覆盖多个有效等价类）； 无效等价类必须逐个单独覆盖（一个测试用例只包含一个无效等价类）。 原因：若一个用例同时含两个无效输入，出错时无法定位是哪一个导致的。

完整示例：某登录系统规定"密码为 6~18 位字符，只能含字母和数字"

输入条件 有效等价类 无效等价类
长度 ① 6 ≤ 长度 ≤ 18 ④ 长度 < 6；⑤ 长度 > 18
字符 ② 只含字母数字；③（可并入②） ⑥ 含特殊字符（如 @）；⑦ 含空格

测试用例设计： - 有效（合并覆盖）：abc123（长度 8、只含字母数字）→ 覆盖 ①② - 无效（逐个覆盖）：ab1（④）、abcdefghij1234567890（⑤）、ab@123（⑥）、ab 123（⑦）

5.2 边界值分析法

核心思想：大量错误发生在输入/输出范围的边界上，而不是中间。它是等价类划分的补充——等价类只取"中间代表"，边界值专挑边界附近的点。

取值规则（必背）：对范围 [min, max]，通常取

min−1, min, min+1, max−1, max, max+1    （共 6 个点：内边界两侧各取 2 个 + 外边界各 1 个）

示例：成绩范围 [0, 100] - 等价类：有效 {0~100}、无效 {<0}、{>100} - 边界值：−1, 0, 1, 99, 100, 101

⚠️ 易错点：边界值不是只取 min 和 max！题目常把"0 和 100"作为完整答案设为错误选项。标准做法是取边界两侧的值。

5.3 因果图法

适用场景：当输入条件之间存在逻辑组合/约束关系（不是简单独立判断）时，等价类划分难以处理，用因果图。

因果图法四步： 1. 分析需求，列出原因（输入条件）与结果（输出动作）； 2. 画出因果图（用逻辑符号 ∧与、∨或、~非 表示原因到结果的逻辑）； 3. 标注约束（互斥 E、唯一 O、包含 I、屏蔽 R、强制 M 等）； 4. 将因果图转换为判定表（每一列是一条规则），为判定表的每一列设计一个测试用例。

因果图基本符号：

  原因 C1 ──∧── 结果 E     （与：C1、C2 皆真才有 E）   C1 ──┐
  原因 C2 ──┘                                          ├──∧──► E

  原因 C1 ──┐                                          C1 ──┐
            ├──∨── 结果 E   （或：任一为真即有 E）           ├──∨──► E
  原因 C2 ──┘                                          C2 ──┘

  原因 C1 ──~── 结果 E     （非：C1 为真则 E 为假）

约束符号：E（互斥）：两个原因不能同时为真；O（唯一）：恰好一个为真；I（包含）：至少一个为真；R（要求）：一个真则另一个必须真；M（屏蔽）：一个真则另一个必须假。

⚠️ 常考结论：因果图法最终要转换为判定表来生成测试用例。判定表的列数 ≤ 原因组合的全排列数（通过无关条件化简可以合并）。

方法 思路
错误推测法 依靠测试人员的经验与直觉，列出可能出错的地方（如输入 0、负数、空串、最大值、SQL 关键字）
场景法 用业务场景（用例的基本流 + 备选流）组织测试用例

六、白盒测试：逻辑覆盖（必考核心）

白盒测试把程序看作透明的白盒子，依据程序的内部结构和执行路径设计测试用例。核心问题：如何度量"我的测试覆盖了多少代码"。

6.1 逻辑覆盖的六个标准（必背强度递进）

软考标准答案的强度顺序（从弱到强）： 语句覆盖 < 判定覆盖 < 条件覆盖 < 判定-条件覆盖 < 条件组合覆盖 < 路径覆盖

标准 定义 关注点
语句覆盖 每条语句至少执行一次 最弱——只保证语句被执行过
判定覆盖（分支覆盖） 每个判定的每个分支（真/假） 至少执行一次 判定被取到真、也取到假
条件覆盖 每个基本条件（不可再分的原子条件）的真/假 至少执行一次 条件，不是判定
判定-条件覆盖 既满足判定覆盖又满足条件覆盖 判定 + 条件都覆盖
条件组合覆盖 每个判定中所有条件的各种取值组合至少执行一次 组合（多重条件覆盖）
路径覆盖 程序中所有可能的执行路径至少执行一次 最强——穷尽路径

6.2 示例伪代码（本文统一使用这一段）

下面这段代码含两个判定、三个条件（D1 是复合判定，D2 是单条件判定），是软考最典型的考法。我们用它给出每个覆盖标准的最小测试用例集。

void f(int a, int b) {
    if (a > 0 && b > 0) {     // 判定 D1：条件 C1=(a>0), C2=(b>0)
        a = a + 1;            // 语句 S1
    }
    if (a > 5) {              // 判定 D2：条件 C3=(a>5)  —— 注意 a 可能已被 S1 修改
        b = b + a;            // 语句 S2
    }
}

控制流图（CFG）：

        ┌─────────────────────────────┐
        │  ①  a>0 && b>0 ?   (D1)     │
        └────────┬────────────┬───────┘
            真  │            │  假
                ▼            │
        ┌──────────────┐     │
        │  ②  a = a+1  │     │   (S1)
        └──────┬───────┘     │
               │             │
               └──────┬──────┘
                      ▼
        ┌─────────────────────────────┐
        │  ③  a > 5 ?         (D2)    │
        └────────┬────────────┬───────┘
            真  │            │  假
                ▼            │
        ┌──────────────┐     │
        │  ④  b = b+a  │     │   (S2)
        └──────┬───────┘     │
               │             │
               └──────┬──────┘
                      ▼
        ┌──────────────┐
        │  ⑤  出口      │
        └──────────────┘
  • 节点 N = 5（①②③④⑤），边 E = 6（①→②、①→③、②→③、③→④、③→⑤、④→⑤）
  • McCabe 圈复杂度 V(G) = E − N + 2 = 6 − 5 + 2 = 3（计算方法见第七节）
  • 全部可能路径共 4 条（但 V(G)=3，说明独立路径只有 3 条——第 4 条可由其他路径线性组合得到）：
路径 节点序列 条件组合 (D1,D2) 举例输入 (a,b)
P1 ①→③→⑤ (F, F) (0, 0)
P2 ①→③→④→⑤ (F, T) (6, 0)
P3 ①→②→③→⑤ (T, F) (1, 1)
P4 ①→②→③→④→⑤ (T, T) (5, 1)

验证 P2：a=6,b=0 → D1: 6>0 && 0>0 = 假（b=0）→ a 保持 6 → D2: 6>5 = 真。✓ 验证 P4：a=5,b=1 → D1: 5>0 && 1>0 = 真 → S1: a=6 → D2: 6>5 = 真。✓

6.3 每个覆盖标准的最小测试用例集

以下每一行的用例集，都经过逐条验算，确实满足该覆盖标准的定义。请务必自己再算一遍。

（1）语句覆盖（最弱，1 个用例）

需要 S1、S2 都执行一次 → D1 真（执行 S1）、D2 真（执行 S2）。

用例 a b D1 S1 后 a D2 覆盖语句
T1 5 1 真 6 真 S1 ✓、S2 ✓

→ 最小用例数 = 1。

（2）判定覆盖 / 分支覆盖（2 个用例）

需要 D1 取真和假、D2 取真和假。

用例 a b D1 S1 后 a D2 覆盖分支
T1 5 1 真 6 真 D1真 ✓、D2真 ✓
T2 0 0 假 0 假 D1假 ✓、D2假 ✓

→ 最小用例数 = 2。（顺带也达到了语句覆盖）

（3）条件覆盖（2 个用例）

需要 C1=(a>0)、C2=(b>0)、C3=(a>5) 各取真和假。

用例 a b C1(a>0) C2(b>0) D2 处的 a C3(a>5)
T1 5 1 真 真 6（S1 后） 真
T2 0 0 假 假 0 假

→ 最小用例数 = 2（C1/C2/C3 的真、假都出现）。

⚠️ 高频陷阱（必看）：条件覆盖并不必然包含判定覆盖！ 反例：若选 a=1,b=0 与 a=0,b=1： - T3: a=1,b=0 → C1=真、C2=假 ✓（两个条件都覆盖到了） - T4: a=0,b=1 → C1=假、C2=真 ✓ 但 D1 = a>0 && b>0 在两个用例中都为假——D1 的"真"分支从未执行，S1 从未被覆盖！ 结论：条件覆盖与判定覆盖是部分独立的关系，所以才有下一级"判定-条件覆盖"把它们合起来。

（4）判定-条件覆盖（2 个用例）

同时满足判定覆盖与条件覆盖。

用例 a b C1 C2 D1 C3 D2
T1 5 1 真 真 真 真 真
T2 0 0 假 假 假 假 假

→ 最小用例数 = 2。所有条件的真/假 ✓，所有判定的真/假 ✓。

（5）条件组合覆盖（4 个用例）

定义：每个判定内部的所有条件取值组合都要出现（D1 的组合是 C1×C2，D2 只有一个条件，组合就是 C3 的真/假）。 ⚠️ 不是把 D1 的组合与 D2 的组合做全排列（那是"跨判定组合"，超出标准定义）。

D1 需要的 4 种组合：(C1,C2) ∈ {(真,真)、(真,假)、(假,真)、(假,假)} D2 需要的 2 种取值：C3 ∈ {真、假}

用例 a b (C1,C2) D1 D2 处的 a C3 D2
T1 5 1 (真,真) 真 6 真 真
T2 1 0 (真,假) 假 1（D1假，a 不变） 假 假
T3 0 1 (假,真) 假 0 假 假
T4 0 0 (假,假) 假 0 假 假

逐条验算： - T1: C1=(5>0)=真，C2=(1>0)=真 → (真,真) ✓；D1 真 → a=6 → C3=(6>5)=真 ✓ - T2: C1=(1>0)=真，C2=(0>0)=假 → (真,假) ✓；D1 假 → a 不变=1 → C3=(1>5)=假 ✓ - T3: C1=(0>0)=假，C2=(1>0)=真 → (假,真) ✓；D1 假 → a=0 → C3=(0>5)=假 ✓ - T4: C1=(0>0)=假，C2=(0>0)=假 → (假,假) ✓；D1 假 → a=0 → C3=(0>5)=假 ✓ - C3 的"真"由 T1 覆盖 ✓，"假"由 T2/T3/T4 覆盖 ✓

→ 最小用例数 = 4。

⚠️ 重要观察（常考）：这 4 个用例走过的路径只有 P4（T1）与 P1（T2、T3、T4） 两条。 P2（①→③→④→⑤，D1假 D2真）与 P3（①→②→③→⑤，D1真 D2假）从未被执行！ 结论：条件组合覆盖并不保证覆盖所有路径。

（6）路径覆盖（4 个用例）

需要 4 条路径全部走一遍：

用例 a b 路径 (D1,D2)
T1 0 0 P1: ①→③→⑤ (F,F)
T2 6 0 P2: ①→③→④→⑤ (F,T)
T3 1 1 P3: ①→②→③→⑤ (T,F)
T4 5 1 P4: ①→②→③→④→⑤ (T,T)

逐条验算： - T1: D1=(0>0 && 0>0)=假，a=0，D2=(0>5)=假 → ①→③→⑤ = P1 ✓ - T2: D1=(6>0 && 0>0)=假（b=0），a 保持 6，D2=(6>5)=真 → ①→③→④→⑤ = P2 ✓ - T3: D1=(1>0 && 1>0)=真，S1: a=2，D2=(2>5)=假 → ①→②→③→⑤ = P3 ✓ - T4: D1=(5>0 && 1>0)=真，S1: a=6，D2=(6>5)=真 → ①→②→③→④→⑤ = P4 ✓

→ 最小用例数 = 4（本例路径数为 4）。

⚠️ 反向观察（也常考）：这 4 个用例覆盖的条件组合是 T1→(C1,C2)=(假,假)、T2→(真,假)、T3→(真,真)、T4→(真,真)。 (假,真) 这个组合从未出现（即 a≤0 且 b>0 的输入）。 结论：路径覆盖也不保证覆盖所有条件组合。

6.4 覆盖强度的严格说明（深入辨析）

考试标准答案的强度排序（从弱到强）：
  语句覆盖 < 判定覆盖 < 条件覆盖 < 判定-条件覆盖 < 条件组合覆盖 < 路径覆盖

严格来说，末两级"不可比"（6.3 的两组用例已经证明了这一点）：

事实 说明
条件组合覆盖 不含 路径覆盖 6.3(5) 的 4 个用例只走了 P1、P4 两条路径，漏掉 P2、P3
路径覆盖 不含 条件组合覆盖 6.3(6) 的 4 个用例从未让 (C1,C2) 出现 (假,真) 组合

考场策略：选择题按"语句<判定<条件<判定-条件<条件组合<路径"作答（这是软考教程的官方表述）；若题目问"条件组合覆盖是否一定覆盖所有路径"，答案是否。

还有两个易错结论： - 判定覆盖 ⊇ 语句覆盖（每个分支都走过，语句必然都执行过）——但反过来不成立。 - 条件覆盖 ⊄ 判定覆盖，判定覆盖 ⊄ 条件覆盖（二者互不包含，故需判定-条件覆盖）。

七、McCabe 圈复杂度与基本路径测试

7.1 圈复杂度 V(G) 的三种算法

圈复杂度由 Thomas J. McCabe 于 1976 年在《A Complexity Measure》中提出，用于度量程序控制流的复杂度。

方法 公式 说明
① 边节点法 V(G) = E − N + 2 E=控制流图的边数，N=节点数（含出口节点）
② 判定节点法 V(G) = P + 1 P=判定（谓词）节点数；每个判定节点加 1
③ 区域数法 V(G) = 区域数 + 1 画平面图，数出区域（含图外部的无限区域）

⚠️ 易错点：方法①的常数是 +2（不是 +1），因为公式默认把"程序外部到入口"和"出口到程序外部"各算作一条隐含的边。三种方法结果必然一致，可用作交叉验证。

以 6.2 的示例验算三种方法： - 边节点法：E=6, N=5 → V = 6−5+2 = 3 - 判定节点法：判定节点为 ①(D1)、③(D2)，P=2 → V = 2+1 = 3 ✓ - 区域数法：平面图被分成 2 个有限区域（①②③围成的小区域、③④⑤围成的小区域）+ 1 个外部无限区域 → V = 2+1 = 3 ✓

7.2 V(G) 的含义与建议阈值

  • V(G) = 从入口到出口的线性独立路径的条数（精确值，不是"上界"也不是"下界"）——也就是基本路径测试所需的最少测试用例数；
  • V(G) 越大，程序越复杂、越难测试和维护；
  • McCabe 建议：V(G) ≤ 10，超过则应考虑拆分模块。

7.3 基本路径测试四步法（必考流程）

第 1 步：根据源代码（或流程图）画出控制流图（CFG）
第 2 步：计算圈复杂度 V(G)（用 E−N+2，再用 P+1 交叉验证）
第 3 步：确定 V(G) 条"独立路径"（基本路径集）
         —— 独立路径：至少包含一条其他路径未曾走过的"新边"的路径
第 4 步：为每条独立路径设计一个测试用例（代入输入，推出预期输出）

⚠️ 独立路径 ≠ 全部路径：V(G)=3 意味着独立路径只有 3 条，但程序可能的总路径数可以更多（6.2 的例子总路径 4 条，独立路径 3 条）。基本路径测试只覆盖独立路径集，这是它与"路径覆盖"的关键区别。

7.4 含循环的例子（重点：回边处理）

int sum(int n, int m) {
    int i = 0, s = 0;
    while (i < n) {          // 判定 D1
        if (m > 0)           // 判定 D2
            s = s + i;       // 语句 S1
        i = i + 1;           // 语句 S2
    }
    return s;                // 语句 S3
}

控制流图：

                       ┌──────────────────────────┐
           └──────────▶│ ①  i < n ?       (D1)    │
           │           └─────┬─────────────┬──────┘
           │     真           │             └ 假
           │                 ▼              ───────────┐
           │           ┌──────────────────────────┐    │
           │           │ ②  m > 0 ?       (D2)    │    │
           │           └─────┬─────────────┬──────┘    │
           │     真           │           假 │           │
           │                 ▼             ▼           │
           │ ┌─────────────────┐  ┌────────────────┐   │
           │ │ ③  s = s+i      │─▶│ ④  i = i+1     │   │ (S1)
           │ └─────────────────┘  └───────┬────────┘   │ (S2)
           ┌──────────────────────────────└            │ （回边 ④→①）
                                                       │
                                                       ▼
                                           ┌────────────────┐
                                           │ ⑤  return s    │(S3)
                                           └────────────────┘
  • 节点 N=5，边 E=6（①→②、①→⑤、②→③、②→④、③→④、④→①）
  • V(G) = E − N + 2 = 6 − 5 + 2 = 3；判定节点 P=2（①②）→ P+1 = 3 ✓

3 条独立路径：

路径 节点序列 含义 测试用例 (n, m)
B1 ①→⑤ 一次都不进入循环 n=0, m=0
B2 ①→②→④→①→⑤ 进入循环且 D2 为假 n=1, m=0
B3 ①→②→③→④→①→⑤ 进入循环且 D2 为真 n=1, m=1

验算： - B1: n=0 → D1(0<0)=假 → 直接 ⑤，return 0 ✓ - B2: n=1,m=0 → i=0<1 真 → D2(0>0)=假 → i=1 → 回边 ①：1<1 假 → ⑤，return 0 ✓ - B3: n=1,m=1 → i=0<1 真 → D2(1>0)=真 → s=s+0=0, i=1 → 回边 ①：1<1 假 → ⑤，return 0 ✓

注意：循环体执行多圈的路径（如 ①→②→③→④→①→②→④→①→⑤）在图论上可由基本路径线性组合得到，因此不属于独立路径集——基本路径测试不要求穷尽所有循环次数。

八、软件维护的四种类型（复习 + 深化）

Day 12 已给出分类，本节补充判别技巧（考试常以"场景题"形式出现）。

维护类型 目的 触发场景 占比
改正性维护（纠错性） 改正交付后发现的错误（程序本身有 bug） "系统计算结果偶发出错" ~20%
适应性维护 适应外部环境变化（不改功能） "操作系统/数据库升级后系统不能运行""税率政策调整" ~25%
完善性维护 增加新功能、改进性能、提升体验（用户想要更多更好） "用户要求增加报表""加快查询速度" ~50%（最大）
预防性维护 主动改进以提高可维护性、防患未然 "重构老旧代码、补充文档以降低未来风险" ~5%

判别两步法：

第 1 步：问题的"变化"来自哪一侧？
   系统本身有错（交付时就有缺陷）          → 改正性维护
   外部环境变了（OS/硬件/法规/数据格式）    → 适应性维护
   用户想要更多/更好（新需求、性能提升）    → 完善性维护
   主动为未来买保险（提高可维护性）         → 预防性维护

第 2 步（区分完善性 vs 适应性）：
   "系统仍然能跑，只是用户不满意想要更多" → 完善性
   "系统跑不起来了/格式不对了，因为环境变了" → 适应性

⚠️ 最高频陷阱： - "增加一个统计报表功能" → 完善性（用户想要更多），不是适应性； - "系统在 Windows 11 上无法启动" → 适应性（环境变了），不是改正性（交付时本就是好的）。

九、项目管理基础

9.1 成本与工作量估算（了解）

方法 说明
代码行估算（LOC） 估算源代码行数 → 乘以每行成本
功能点分析（FPA） 从外部输入/输出、外部查询、内部逻辑文件、外部接口等功能维度估算，与实现语言无关
COCOMO 模型 构造性成本模型：E = a × (KLOC)^b，精确度分基本/中级/详细三档
类比估算 / 参数估算 参照历史相似项目 / 用统计模型参数估算

9.2 进度管理：甘特图与 PERT/CPM

① 甘特图（Gantt，1910s 由 Henry Gantt 提出）

任务      1月  2月  3月  4月  5月
需求分析  ████
概要设计      ████
详细设计          ████
编码                  ████████
测试                          ████
  • 优点：直观、简单、清楚地表示每个任务的开始/结束时间与持续时长；
  • 缺点：不能清楚地表示任务之间的依赖关系，也无法确定关键路径与关键任务——这是高频考点。

② PERT 图 / CPM（关键路径法）

PERT（1958 美国海军北极星计划）与 CPM（1957 杜邦公司）都使用 AOE 网：
  顶点 = 事件（里程碑），边 = 活动，边上的权 = 活动耗时。
  • 能清楚表示任务间依赖关系；
  • 能求出关键路径。

③ 关键路径（必考）

在 AOE 网中，关键路径 = 从源点到汇点（开始事件到完成事件）的所有路径中，耗时最长的那条。 关键路径的长度 = 整个工程的最短完成时间。

关键路径的性质：
  1. 关键路径上所有活动的"最早开始时间 = 最迟开始时间"（缓冲时间/松弛时间为 0）
  2. 关键路径上任一活动延期，都会导致整个工程延期
  3. 关键路径可能不止一条（多条并列时，缩短其一未必缩短总工期）
  4. 想缩短工期，必须缩短【所有】关键路径上的活动

简单示例：

事件：①──(A,3)──②──(C,4)──④──(E,2)──⑤
              │              │
              └──(B,2)──③──(D,6)──┘

路径 ①→②→④→⑤：3+4+2 = 9
路径 ①→②→③→④→⑤：3+2+6+2 = 13   ← 最长，为关键路径

→ 总工期 = 13；A、C、E 是非关键活动，B、D（在最长路径上）是关键活动。

⚠️ 易错点：关键路径是最长路径，但它代表的是最短完成时间——"最长"指的是路径上活动耗时之和最大。

9.3 风险管理

风险管理四步骤：

风险识别 → 风险估计（分析） → 风险评价 → 风险控制（应对）

风险估计的核心公式（必考）：

$$风险暴露（风险代价）\ RE = P \times L$$

其中 P = 风险发生的概率，L = 风险发生后的损失。

例：某风险发生概率 25%，一旦发生损失 80 万元 → RE = 0.25 × 80 = 20 万元。这 20 万元是"为应对该风险值得投入的上限"。

风险应对的四种策略：

策略 做法 例子
规避（避免） 改变计划，消除风险源 放弃不成熟的技术方案
转移 把风险的后果转给第三方 购买保险、外包给专业厂商
减轻 降低发生概率或损失 增加测试、做原型验证
接受 承认并承担（自担风险） 对小概率低损失风险设立储备金

十、本日速查与记忆口诀

10.1 一页纸结论（建议默写）

  1. 设计原则：单开里接依（SRP/OCP/LSP/ISP/DIP，SOLID）+ 迪米特（最少知识）+ 合成复用（组合优于继承）。
  2. 开闭原则是核心目标；依赖倒置、里氏替换、接口隔离是实现开闭的手段。
  3. 耦合七级（低→高）：无直、数、标、控、外、公、内；内容耦合最严重，必须避免。
  4. 内聚七级（低→高）：偶、逻、时、过、通、顺、功；功能内聚最理想。
  5. 过程内聚 vs 顺序内聚：前者输出不是后者输入 → 过程；是输入 → 顺序。
  6. 单元测试依据详细设计、集成测试依据概要设计、系统测试依据 SRS。
  7. 自顶向下集成需要桩模块；自底向上集成需要驱动模块。
  8. 黑盒三方法：等价类划分、边界值分析、因果图（转判定表）；白盒核心是逻辑覆盖 + 基本路径。
  9. 边界值取 min−1, min, min+1, max−1, max, max+1（不是只取 min、max）。
  10. 有效等价类可合并；无效等价类必须逐个单独测。
  11. 覆盖强度（弱→强）：语句 < 判定 < 条件 < 判定-条件 < 条件组合 < 路径。
  12. 条件覆盖不保证判定覆盖（两者互不包含）→ 需判定-条件覆盖。
  13. 圈复杂度 V(G) = E − N + 2 = P + 1 = 区域数 + 1；McCabe 建议 V(G) ≤ 10。
  14. 基本路径测试四步：画 CFG → 算 V(G) → 找 V(G) 条独立路径 → 每条路径设计一个用例。
  15. 维护四类型：改正（改错）/ 适应（环境变）/ 完善（加功能，占 ~50% 最大）/ 预防（为未来）。
  16. 关键路径是 AOE 网中最长路径，其长度 = 工程最短完成时间；关键活动缓冲时间为 0。
  17. 风险暴露 RE = P × L（概率 × 损失）；风险应对：规避、转移、减轻、接受。
  18. 甘特图不能清楚表示任务依赖、不能求关键路径。

10.2 高频陷阱清单

陷阱 正确说法
"耦合越低越好，所以模块间最好不要任何联系" 无直接耦合最低，但系统总要通过模块协作完成功能；目标是低耦合高内聚，不是零耦合
"传了多个参数就是高耦合" 耦合级别看传的是什么：简单值=数据耦合（低），控制标志=控制耦合（较高）
"内聚高就是模块大而全" 内聚高指围绕单一职责；大而全反而是偶然/逻辑内聚（低）
"边界值取 0 和 100 就够了" 要取 −1, 0, 1, 99, 100, 101（边界两侧）
"条件覆盖一定能覆盖判定" 不一定（见 6.3(3) 反例）
"条件组合覆盖 = 覆盖所有路径" 不是，条件组合覆盖可能漏路径（见 6.3(5)）
"V(G) = E − N + 1" 是 +2；也可用 P+1 交叉验证
"独立路径数 = 全部路径数" 独立路径数 = V(G)；总路径数可以更多（循环时甚至无限）
"关键路径是最短路径" 关键路径是最长路径，代表最短完成时间
"增加报表功能属于适应性维护" 属于完善性维护
"系统升级 OS 后不能运行是改正性维护" 属于适应性维护（环境变了）
