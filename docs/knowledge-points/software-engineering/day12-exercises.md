## 附：Day 12 笔记「一页纸结论」速答

1. 生命周期三时期：**定义、开发、运行维护**；**维护**阶段时间最长、花费最大。
2. 可行性研究四类：**经济（钱）、技术（技）、法律（法）、操作（人）**。
3. **瀑布 = 文档驱动**；**V = 开发测试对应**；**增量 = 分批交付**；**原型 = 澄清需求**；**螺旋 = 风险驱动**；**敏捷 = 拥抱变化**。
4. **螺旋 = Boehm 1988**；四象限顺序：**制定计划 → 风险分析 → 实施工程 → 客户评估**。
5. V 模型对应：**需求↔验收、概设↔系统、详设↔集成、编码↔单元**。
6. 敏捷四价值观：**个体互动 / 可工作软件 / 客户合作 / 响应变化**（高于右项，但不否定右项）。
7. Scrum：**3 角色 / 3 工件 / 5 事件**；Sprint **2–4 周**；每日站会 **15 分钟**。
8. 需求三分类：**功能 / 非功能（性能在此）/ 设计约束**。
9. SRS 七性质：**正确、无歧义、完整、一致、可验证、可修改、可追踪**。
10. **DFD 四要素 = 外部实体（矩形）+ 加工（圆角矩形）+ 数据流（箭头）+ 数据存储（双横线）**。
11. **DFD 只有数据流、没有控制流**；每个数据流必须命名。
12. **父子图平衡**：子图外部流与父加工数据流**数量、方向、名称一致**。
13. DD 符号：**`= 定义、+ 与、| 或、{ } 重复、( ) 可选`**。
14. 小说明三工具：**结构化语言、判定表、判定树**；判定表四部分：**条件桩、条件项、动作桩、动作项**。
15. 增量 vs 原型：**"增量交产品，原型定需求"**。

## 答案与解析

> **答案速查**：1.B　2.C　3.C　4.B　5.B　6.B　7.B　8.C　9.C　10.B　11.B　12.D　13.C　14.A　15.B　16.B　17.C　18.C　19.C　20.C

**1. 答案：B**
- **解析**：螺旋模型 = **Boehm 1988**，最本质特征是**风险驱动**——每一圈都做风险分析、用（常常是原型的）手段化解风险。
- **A 干扰项**：文档驱动是**瀑布模型**。**C 干扰项**：螺旋会用到原型，但原型是"风险分析"象限中的**手段**，不是驱动目的——这正是螺旋与原型最容易混的地方。**D 干扰项**：数据流驱动是**结构化分析（SA）方法**，不是过程模型。
- **知识点**：`day12-process.md` §2.5、§2.7 对比表。

**2. 答案：C**
- **解析**：V 模型的四对对应关系：**需求分析↔验收测试、概要设计↔系统测试、详细设计↔集成测试、编码↔单元测试**。
- **B 干扰项**：集成测试对应**详细设计**——把"概设/详设"与"系统/集成"配对颠倒是最常见的错误。**A 干扰项**：单元测试对应编码。**D 干扰项**：验收测试对应需求分析。
- **记忆链**：越靠左的开发文档对应越靠右的测试阶段；详细设计比概要设计更"细"，所以对应更底层的集成测试。
- **知识点**：`day12-process.md` §2.2、§2.8 辨析③。

**3. 答案：C**
- **解析**：瀑布模型要求**需求明确且稳定**，恰恰**不能**快速响应需求变化——这是它最大的缺点（风险后移、错误积累到后期）。
- **A、B、D** 都是瀑布模型的正确描述：线性顺序+阶段评审、文档驱动、用户很晚才见到可运行产品。
- **知识点**：`day12-process.md` §2.1。

**4. 答案：B**
- **解析**：增量模型交付的每个增量都是**可运行产品的一部分**，最终累积成完整系统（产物保留）；原型模型构造原型主要是为了**澄清/验证需求**（抛弃型用完即弃）。一句话：**"增量交产品，原型定需求"**。
- **A 干扰项**：反了——原型模型才构造原型。**C 干扰项**：也反了——分批交付的是**增量模型**。**D 干扰项**：增量模型常用于需要**快速交付核心功能**的项目（并不限于小型），原型模型也常用于**小型/界面驱动**系统，两者都不是按"项目规模大小"划分的。
- **知识点**：`day12-process.md` §2.3、§2.4、§2.8 辨析②。

**5. 答案：B**
- **解析**：螺旋模型由 **Barry Boehm** 于 **1988** 年在《A Spiral Model of Software Development and Enhancement》（IEEE Computer）中提出。
- **A 干扰项**：W. W. Royce 于 **1970** 年提出**瀑布模型**。**C 干扰项**：Tom DeMarco 于 1978 年系统化**结构化分析（SA）**方法。**D 干扰项**：Ivar Jacobson 是**用例/OOSE/RUP** 的代表人物（Day 14 会再见到）。
- **知识点**：`day12-process.md` §2.5、§2.7。

**6. 答案：B**
- **解析**：敏捷四价值观之一是"**可工作的软件 高于 详尽的文档**"。注意四条价值观的左项各不相同，不能串接：**个体互动 > 流程工具**；**可工作软件 > 详尽文档**；**客户合作 > 合同谈判**；**响应变化 > 遵循计划**。
- **A/C/D 干扰项**：把某条价值观的左项硬配到另一条的右项上，是典型的"张冠李戴"型干扰。
- **知识点**：`day12-process.md` §2.6。

**7. 答案：B**
- **解析**：Scrum Master 是**服务型领导**：服务团队、消除障碍、推进并维护 Scrum 流程。
- **A 干扰项**：管理 Product Backlog 优先级是**产品负责人（Product Owner）**的职责。**C 干扰项**：写代码是**开发团队**的职责。**D 干扰项**：Scrum 中没有"代表客户逐项验收"这一角色；验收体现在 **Sprint 评审会议**上。
- **知识点**：`day12-process.md` §2.6（Scrum 3-3-5）。

**8. 答案：C**
- **解析**：需求不明确 + 界面占主导 + 小型 → **原型模型**（快速构造原型、用户试用反馈、迭代明确需求）。
- **A/B 干扰项**：瀑布与 V 模型都要求**需求明确**，与题干"需求不明确"矛盾。**D 干扰项**：增量模型适合"需求可分优先级、需快速交付核心功能"，但其前提是需求大体明确、只是分批实现；本题的核心痛点是"需求说不清"，原型模型才是对症的。
- **知识点**：`day12-process.md` §2.4、§2.7。

**9. 答案：C**
- **解析**：**演化型原型**（演进型）的原型会被保留并逐步迭代，最终**演化为交付系统**；**抛弃型原型**（探索型/实验型）仅用于明确需求，**用完即弃**，正式系统重新开发。
- **A 干扰项**：描述的是抛弃型。**B 干扰项**：把两种变种的处置方式颠倒。**D 干扰项**：两者的关键区别恰恰就是对原型的最终处置。
- **知识点**：`day12-process.md` §2.4 变种表。

**10. 答案：B**
- **解析**：螺旋每圈的四个活动顺序为：**制定计划（目标/替代方案/约束）→ 风险分析（评估替代、识别并化解风险）→ 实施工程（开发与验证）→ 客户评估（评价成果、规划下一圈）**。
- **A 干扰项**：把"风险分析"提到"制定计划"之前——风险分析必须先有"计划"中确定的目标和备选方案才能评估。**C 干扰项**：风险分析在实施之前进行（否则就不叫"风险驱动"了）。**D 干扰项**：客户评估是**每圈的收尾**，不是起点。
- **知识点**：`day12-process.md` §2.5 四象限。

**11. 答案：B**
- **解析**：需求明确 + 安全性极高 + 要求测试与开发紧密对应 → **V 模型**（开发与测试一一对应，测试用例可在完成开发文档后立即设计）。
- **A 干扰项**：瀑布模型同样适合需求明确的项目，但它**不强调**测试与开发的逐级对应关系；题干明确要求"测试活动能与开发活动紧密对应、尽早设计测试用例"，这正是 V 模型的核心特征。**C 干扰项**：螺旋适合**大型、复杂、高风险**项目，且代价是高昂的风险分析成本——本题项目需求明确，并非高风险的大型探索性项目。**D 干扰项**：敏捷适合需求**变化频繁**的场景，与题干"需求明确、安全要求极高"的稳定语境相反。
- **知识点**：`day12-process.md` §2.2、§2.7。

**12. 答案：D**
- **解析**：**运行与维护**阶段占软件生命周期的大部分时间与成本（经验上占总成本的 60%–80%）。这也是为什么"可维护性"是软件质量的重要属性。
- **A/B/C 干扰项**：需求分析、编码、测试都属于**开发期**，时间远短于维护期。
- **知识点**：`day12-process.md` §1.1、§1.2。

**13. 答案：C**
- **解析**：维护四类型：改正性（改错）、适应性（适应环境变化）、**完善性（增加新功能、改进性能与体验，占比最大）**、预防性（提高可维护性）。**增加新报表 = 增加新功能 = 完善性维护**。
- **B 干扰项（最易选错）**：适应性维护针对的是**环境变化**（OS 升级、硬件更换、业务规则被外部改变），而不是用户新提出的功能诉求。判别标准：**"用户想要更多/更好"→ 完善性；"环境变了导致系统不适应"→ 适应性**。
- **A 干扰项**：改正性维护是**改交付后发现的错误**，本题系统本身没有错。**D 干扰项**：预防性维护是**主动提高可维护性**的改造，不是为了加功能。
- **知识点**：`day12-process.md` §1.4。

**14. 答案：A**
- **解析**：可行性研究分四类：**经济（钱）、技术（技）、法律（法）、操作（人）**。成本-效益分析（投资回收期、净现值、投入产出比）评估"值不值得做"，属于**经济可行性**。
- **B 干扰项**：技术可行性评估"做得了吗"（技术方案、资源、风险）。**C 干扰项**：法律可行性评估知识产权、合同、合规。**D 干扰项**：操作可行性评估用户用不用得起来、业务流程跑不跑得通。
- **知识点**：`day12-process.md` §1.3。

**15. 答案：B**
- **解析**：响应时间、并发数、可用性、可靠性、安全性等都属于**非功能需求**（质量属性）。
- **A 干扰项（最易选错）**：功能需求描述"系统提供什么功能/服务"（如"用户可以查询图书"），而性能指标不是功能本身。**C 干扰项**：设计约束是"必须遵守的限制"（如必须用某种语言/平台）。**D 干扰项**：业务需求是组织层面的目标（如"提高借阅量 20%"），不是系统性能指标。
- **知识点**：`day12-process.md` §3.2。

**16. 答案：B**
- **解析**：SRS 七性质：正确、**无歧义**、完整、一致、可验证、可修改、可追踪。"每条需求只有一种解释"= **无歧义性**（不能出现"大概""可能""较快"这类含糊表述）。
- **A 干扰项**：正确性指需求**准确描述**系统应具有的行为。**C 干扰项**：完整性指**覆盖所有**需要的需求、没有遗漏。**D 干扰项**：可验证性指每条需求都能**通过测试或检查确认**。
- **知识点**：`day12-process.md` §3.4。

**17. 答案：C**
- **解析**：需求获取常用方法：访谈、现场观察、问卷调查、会议（JAD）、原型法、用例分析。**代码审查**属于**软件测试/质量保证**阶段的静态测试方法，此时还没有代码，不可能是需求获取方法。
- **A/B/D**：访谈、问卷、原型法都是标准的需求获取方法。
- **知识点**：`day12-process.md` §3.3。

**18. 答案：C**
- **解析**：DFD 四要素的符号：**外部实体=矩形**、**加工=圆角矩形（或圆形）**、**数据流=带箭头的线**、**数据存储=双横线（开口矩形）**。
- **A 干扰项**：矩形是**外部实体**。**B 干扰项**：圆角矩形是**加工**。**D 干扰项**：菱形在 DFD 中**不是**标准符号（菱形常见于流程图中的判断框或 E-R 图中的联系）。
- **知识点**：`day12-process.md` §4.2。

**19. 答案：C**
- **解析**：DFD **只有数据流、没有控制流**——它**不表示**条件判断、循环、时序等控制逻辑，这是 DFD 与程序流程图的根本区别，也是**高频考点**。判断与循环应放在**加工逻辑（小说明）**中用结构化语言/判定表/判定树描述。
- **A/B/D** 都是 DFD 的正确规范：数据流必须命名；四类要素；父子图平衡（子图外部流与父加工数据流在数量、方向上一致）。
- **知识点**：`day12-process.md` §4.2、§4.3。

**20. 答案：C**
- **解析**：图中"2 还书处理"接收读者的**还书请求**、向读者输出**逾期催还**；从 **D2 借阅记录表**读取借阅记录（箭头由 D2 指向加工），并把更新后的图书状态写回 **D1 图书信息表**（箭头由加工指向 D1）。箭头方向与"读/写"语义一致，符合 DFD 规范。
- **A 干扰项**：父子图平衡考察的是**被分解的那个加工**在父图与子图之间的数据流是否一致，而不是"系统外部实体只出现一次"。本图是 0 层图的局部，读者与其他加工（借书处理、新书入库）的交互在完整 0 层图中另有表示，不能仅凭局部图断定"不平衡"。
- **B 干扰项**：本题设定明确说明"从 D2 读取、向 D1 写回"，与图中箭头方向一致，并非画错。**注意**：箭头方向表示数据流向——**由存储指向加工=读取，由加工指向存储=写入**。
- **D 干扰项**：DFD 中一个加工可以同时连接多个数据存储（读若干个、写若干个），这是极其常见的结构。
- **知识点**：`day12-process.md` §4.3（分层与平衡）、§4.4（完整示例及数据流清单）。
