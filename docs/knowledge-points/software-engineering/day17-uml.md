## 一、UML 总览（先建立全景）

UML（Unified Modeling Language，统一建模语言）用**图形**描述软件系统。UML 2.x 共 **13 种图**，分两大类：

```
UML 图（13 种）
├── 结构图（Structural Diagrams，描述"系统由什么组成"）
│     ├── 类图 Class Diagram        ← 本日重点（下午大题 No.1）
│     ├── 对象图 Object Diagram     ← 2020 下半年卷考过
│     ├── 构件图 Component Diagram
│     ├── 部署图 Deployment Diagram
│     ├── 组合结构图 Composite Structure
│     └── 包图 Package Diagram
└── 行为图（Behavioral Diagrams，描述"系统怎么动"）
      ├── 用例图 Use Case Diagram   ← 本日重点（下午大题常考）
      ├── 活动图 Activity Diagram   ← 本日重点
      ├── 状态机图 State Machine    ← 本日重点（2021 上半年卷考过）
      └── 交互图（4 种）
            ├── 顺序图 Sequence Diagram      ← 本日重点（下午大题常考）
            ├── 通信图/协作图 Communication
            ├── 交互概览图 Interaction Overview
            └── 定时图 Timing Diagram
```

> **一句话总览**：**结构图管"静态"（有什么），行为图管"动态"（做什么）**。下午大题最爱考的 5 种：**类图、用例图、顺序图、状态图、活动图**——正好是本日全部内容。

## 二、类图（最重要，没有之一）

类图描述系统中的**类、类的内部结构（属性/方法）以及类之间的关系**。它是面向对象设计的"骨架"，下午试题三若考 UML，**大概率是类图**。

### 2.1 类的画法（三格矩形）

```text
╭─────────────────────╮
│        学生          │  ← 第一格：类名（抽象类用【斜体】，接口写 <<interface>>）
├─────────────────────┤
│ -  学号 : String     │  ← 第二格：属性（可见性 + 名 : 类型）
│ -  姓名 : String     │
│ #  年龄 : int        │
├─────────────────────┤
│ +  选课(课程) : void  │  ← 第三格：方法（可见性 + 名(参数) : 返回类型）
│ +  退课(课程) : bool  │
╰─────────────────────╯
```

**可见性符号（必背，3+1 个）**：

| 符号 | 可见性 | 范围 | 代码 |
|------|--------|------|------|
| `+` | public（公有） | 所有类可见 | `public` |
| `-` | private（私有） | 仅本类可见 | `private` |
| `#` | protected（受保护） | 本类 + 子类 | `protected` |
| `~` | package（包级） | 同包可见 | （Java 默认） |

> **易错点**：属性前面的 `+/-/#` **不是**"加号/井号装饰"，是可见性；填空题若让填属性，**可见性符号要照抄**（题目给的类图里其它属性是 `-`，新填的属性通常也是 `-`）。

**接口的画法**：两格矩形，顶端标 `<<interface>>`（或用"棒棒糖"表示法——接口名旁画一个圆圈）。

```text
╭─────────────────────╮
│    <<interface>>     │
│      可飞行 Flyable  │
├─────────────────────┤
│ +  fly() : void      │
╰─────────────────────╯
```

### 2.2 类间六种关系（本节是全文最核心，逐字读）

六种关系按**耦合强度从弱到强**：**依赖 < 关联 < 聚合 < 组合 < 泛化 ≈ 实现**。记忆口诀：**"依关聚组泛实"**。

| 关系 | UML 符号 | 一句话语义 | 代码级判别（看见代码就能判） | 强度 |
|------|---------|-----------|---------------------------|------|
| **依赖** Dependency | `┈┈┈▶` 虚线 + 开放箭头 | **"用一下"**：临时使用对方，不长期持有 | 对方出现在**方法的参数、局部变量、返回值**里，或调用了对方的静态方法 | 最弱 |
| **关联** Association | `────▶` 实线 + 开放箭头 | **"认识、长期联系"**：持有对方引用作为成员 | 对方是本类的**成员变量（字段）**，且双方地位平等 | 弱 |
| **聚合** Aggregation | `◆────` 空心菱形 + 实线（菱形在**整体**端） | **"弱的拥有"**：整体包含部分，但**部分可以脱离整体独立存在** | 成员变量，但该对象是**从外部传入/注入**的（整体不管它的生死） | 中 |
| **组合** Composition | `◆◆────` 实心菱形 + 实线（菱形在**整体**端） | **"强的拥有"**：整体与部分**同生共死**，部分不能脱离整体 | 成员变量，且该对象是**整体自己 new 出来的**（构造时创建、销毁时随之销毁） | 强 |
| **泛化** Generalization | `────△` 实线 + 空心三角（三角指向**父类**） | **"is-a"**：继承 | `class A extends B` | 最强 |
| **实现** Realization | `┈┈┈△` 虚线 + 空心三角（三角指向**接口**） | **"实现接口"** | `class A implements I` | 最强（与泛化并列） |

> **菱形永远画在"整体"一端**，这是图形填空题的送分点：看到菱形，菱形那一头就是整体。
> **三角永远指向"更一般/更抽象"的一端**：泛化指向父类，实现指向接口。

**一张图看完六种关系**（"图形绘制系统"示例，分两段画以便阅读）：

**① 泛化 + 实现 + 关联**（类层次部分）：

```text
                     ╭─────────────────────────────╮
                     │       <<interface>>          │
                     │         Drawable             │
                     ├─────────────────────────────┤
                     │ + draw() : void              │
                     ╰──────────────▲──────────────╯
                                    ┆ ← 实现（虚线 + 空心三角，指向接口）
                     ╭──────────────┴──────────────╮
                     │      Shape（图形·抽象类）    │  类名斜体 = 抽象类
                     ├─────────────────────────────┤
                     │ # position : Point           │── 关联（实线箭头）──▶╭──────────────╮
                     ├─────────────────────────────┤                      │   Point      │
                     │ + draw() : void              │                      ├──────────────┤
                     │ + area() : double            │                      │ + x : int    │
                     ╰──────────────▲──────────────╯                      │ + y : int    │
                                    △  ← 泛化（实线 + 空心三角，指向父类）  ╰──────────────╯
                     ╭──────────────┴──────────────╮
                     │                             │
           ╭─────────────────────╮       ╭─────────────────────╮
           │      Circle         │       │     Rectangle       │
           ├─────────────────────┤       ├─────────────────────┤
           │ - radius : double   │       │ - width : double    │
           │                     │       │ - height : double   │
           ├─────────────────────┤       ├─────────────────────┤
           │ + draw() : void     │       │ + draw() : void     │
           │ + area() : double   │       │ + area() : double   │
           ╰─────────────────────╯       ╰─────────────────────╯
```

**② 聚合 + 组合 + 依赖**（整体与部分、使用关系）：

```text
   组合（◆◆ 实心菱形在整体端）：画布内部 new 出图形，图形随画布创建/销毁

   ╭──────────────╮◆◆───────▶╭──────────────────────╮
   │   Canvas     │  组合关系  │        Shape          │
   │  （画布）     │           ╰──────────▲───────────╯
   ├──────────────┤                      ┆ ← 依赖（虚线 + 开放箭头）
   │ - shapes     │          ╭──────────┴───────────╮
   │   : List     │          │      Renderer         │
   ╰──────────────╯          │  （渲染器）            │
                             ├──────────────────────┤
                             │ + draw(Shape s) : void│
                             ╰──────────────────────╯

   聚合（◆ 空心菱形在整体端）：颜色从外部注入，可独立存在、被多处共享

   ╭──────────────╮◆───────▶╭──────────────╮
   │  Palette     │  聚合关系  │    Color      │
   │  （调色板）   │           ├──────────────┤
   ├──────────────┤           │ + r,g,b:int  │
   │ - colors     │           ╰──────────────╯
   │   : List     │
   ╰──────────────╯
```

> **读图检查（能答出这 6 句才算看懂）**：
> ① `Circle/Rectangle ──△ Shape` 是**泛化**（子类指向父类）；② `Shape ┄┄△ Drawable` 是**实现**（虚线，指向接口）；
> ③ `Shape ── Point` 是**关联**（Shape 持有 position 成员）；④ `Canvas ◆◆ Shape` 是**组合**（实心菱形在整体端，图形随画布生死）；
> ⑤ `Palette ◆ Color` 是**聚合**（空心菱形在整体端，颜色可独立/共享）；⑥ `Renderer ┄┄▶ Shape` 是**依赖**（只在方法参数里用到 Shape）。

### 2.3 聚合 vs 组合（高频易错，单独拎出来）

两者都是"整体与部分"，**唯一的判别标准是"部分能否独立存在/生命周期是否绑定"**。

| 维度 | 聚合 Aggregation（空心菱形 ◆） | 组合 Composition（实心菱形 ◆◆） |
|------|------------------------------|-------------------------------|
| 部分**能否脱离整体** | **能**，部分有独立生命周期 | **不能**，部分与整体同生共死 |
| 部分**由谁创建** | 通常外部创建后**注入/传入**整体 | 通常由整体**内部 new**（构造函数中创建） |
| 整体销毁时 | 部分**继续存在**（可被别的整体继续用） | 部分**随之销毁** |
| 关系强度 | 弱的"拥有" | 强的"拥有"（严格的组成） |
| 经典例子 | **球队 ◆ 球员**（球员可转会）、图书馆 ◆ 图书、班级 ◆ 学生 | **车 ◆◆ 引擎/车轮**、人 ◆◆ 四肢、窗体 ◆◆ 按钮 |

**代码判别（最可靠，考场直接套）**：

```java
// 聚合：球员从外部传入，球队不负责创建他
class Team {
    private List<Player> players;      // 通过构造器/setter 从外部注入
    public Team(List<Player> players) { this.players = players; }
}

// 组合：引擎在车内部创建，车报废引擎也不存在了
class Car {
    private Engine engine;             // 车自己 new，不接收外部引擎
    public Car() { this.engine = new Engine(); }   // 同生
    // 车 GC 时，没有任何引用再指向这个 engine → 共死
}
```

> **考场判别口诀**：**"外部注入是聚合，内部创建是组合；整体没了部分还在是聚合，部分跟着没是组合。"**
> **注意反直觉点**：物理上"看起来不可分"的东西（车和引擎）反而**经常被建模成聚合**——因为引擎可以被拆下来装到别的车上。判别看的是**需求语义**，不是物理常识。题目里若写"部件与整体**一起创建、一起销毁**"，才是组合；写"整体**包含**部分、部分**可被共享/独立使用**"，是聚合。

### 2.4 include vs extend（用例图里的高频易错，先在此埋个眼）

类图里没有 include/extend（那是用例图的关系），但两者极易混——详见 §3.3。

### 2.5 多重性（Multiplicity，填空常考）

写在关联线两端的数字，表示"一个对象对应几个对象"：

| 写法 | 含义 | 例子 |
|------|------|------|
| `1` | 恰好一个 | 一个读者有一个借书证 |
| `0..1` | 零个或一个（可选） | 一个员工可以有零个或一个配偶 |
| `*` 或 `0..*` | 零个或多个 | 一个读者可借多本书 |
| `1..*` | 至少一个 | 一个部门至少有一个员工 |
| `n..m` | n 到 m 个 | 一个班 30..50 个学生 |

> **读法**：`读者 1 ──── * 图书` = **一个**读者可对应**多本**图书；反向读：一本图书只能对应一个读者（还书时记录的借阅者唯一）。填空时从需求文字里的数量词（"一个""多个""至少一个"）直接抄。

## 三、用例图（下午大题第 2 常考）

用例图描述**系统功能与参与者（谁用）的交互**，是需求分析阶段的产物（对应 OOA 的功能视图）。

### 3.1 三个基本元素

| 元素 | 符号 | 说明 |
|------|------|------|
| **参与者 Actor** | 小人形（`┌─┐`/简笔） | 与系统交互的**人、设备、时间或外部系统**。不一定是人——定时器、外部系统也可以是 Actor |
| **用例 Use Case** | 椭圆 `╭───╮` | 系统**提供的一项完整功能**。命名用**动宾短语**（"借书"而非"图书"），从参与者角度描述 |
| **系统边界** | 矩形框 | 框内是用例，表示**系统的功能范围**。Actor 一定画在**框外** |

**完整示例（图书借阅系统）**：

```text
  借书 ─────▶╭───────╮       《include》      ╭──────────╮
  ┌──────┐   │       │  ──────────────────▶  │          │
  │      │   │ 借书  │                       │ 身份验证  │
  │ 读者  │───┤       │                       ╰──────────╯
  │      │   ╰───────╯
  │      │   ╭───────╮       《extend》       ╭──────────╮
  │      │   │       │  ◀──────────────────  │          │
  │      │   │ 还书  │                       │ 缴纳罚金  │
  └──────┘   │       │                       ╰──────────╯
     还书 ──▶╰───────╯
                                     ← 系统边界（矩形框）：框内是用例，
  ┌──────┐ 图书入库   ╭──────────╮      Actor（读者、管理员）一定在框外
  │      │───────────▶│          │
  │管理员 │           │ 图书入库  │
  │      │           │          │
  └──────┘           ╰──────────╯
```

> **说明**：椭圆 = 用例；小人形 = Actor（读者、管理员）；外框矩形 = 系统边界。
> 还书时**若逾期**才触发"缴纳罚金"，不逾期则不触发——这就是 extend"可能执行"的含义。

> **说明**：椭圆 = 用例；小人形 = Actor（读者、管理员）；外框矩形 = 系统边界。
> 还书时**若逾期**才触发"缴纳罚金"，不逾期则不触发——这就是 extend"可能执行"的含义。

**读图要点**：
- `读者 ──借书──▶ 借书`：**关联**（实线），Actor 与用例之间只能是关联，**不能**是 include/extend。
- `借书 ──《include》──▶ 身份验证`：借书时**一定**要做身份验证（强制步骤）。
- `缴纳罚金 ──《extend》──▶ 还书`：还书**可能**触发缴罚金（可选分支）。
- Actor 画在系统边界**外面**——填空题让你"指出哪个元素不是用例图的元素"时，记住没有"数据存储"（那是 DFD 的）。

### 3.2 用例间的四种关系

| 关系 | 符号 | 语义 | 执行条件 |
|------|------|------|---------|
| **关联** | 实线（可带箭头） | Actor 与用例之间的交互 | — |
| **包含 include** | 虚线箭头 + `《include》`，**基用例 → 被包含用例** | 把多个用例**共有**的步骤抽出来复用 | **一定执行**（基用例必然触发被包含用例） |
| **扩展 extend** | 虚线箭头 + `《extend》`，**扩展用例 → 基用例** | 给基用例**加可选分支**，基用例本身完整 | **可能执行**（有扩展条件才触发） |
| **泛化 generalization** | 实线 + 空心三角，**子用例 → 父用例** | 子用例是父用例的一种特殊情况 | 父用例可被子用例替换 |

### 3.3 include vs extend（高频易错，两两对照）

| 维度 | 包含《include》 | 扩展《extend》 |
|------|----------------|---------------|
| **箭头方向** | 基用例 ──▶ **被包含用例** | **扩展用例** ──▶ 基用例 |
| **执行性** | **必执行** | **可选**（有条件才执行） |
| **基用例是否完整** | 抽掉被包含用例，基用例**不完整** | 抽掉扩展用例，基用例**仍然完整** |
| **用途** | 复用公共流程（如"身份验证"被借书/还书/查询共用） | 处理可选/异常分支（如"缴纳罚金"只在逾期时发生） |
| **识别关键词** | "每次……都要先……""公共步骤" | "如果……则……""可选""可以……" |

> **箭头方向是最大考点**：两者都是虚线箭头，**方向刚好相反**——
> **include 从"大流程"指向"小流程"**（借书 → 身份验证）；
> **extend 从"附加流程"指向"主流程"**（缴纳罚金 → 还书）。
> 口诀：**"包含必执行，箭头朝小；扩展可选，箭头朝大。"**
> 填空题若让你补全 `《include》` 或 `《extend》` 字样：**先判断"必做还是可选"，再定箭头方向**，两步缺一不可。

## 四、顺序图（下午大题常与类图/用例图配套考）

顺序图（Sequence Diagram）按**时间顺序**展示一组对象之间的消息交互——回答"谁、在什么时候、调用了谁、传了什么"。

### 4.1 四个基本元素

| 元素 | 符号 | 说明 |
|------|------|------|
| **生命线 Lifeline** | 从对象向下的**竖直虚线** | 对象在时间轴上的存在周期，顶端是对象（`对象名:类名`，下划线表示实例） |
| **消息 Message** | 生命线之间的**水平箭头** | 一次方法调用/信息传递 |
| **激活条 Activation** | 生命线上的**窄竖条（控制焦点）** | 该对象**正在执行**的时段（被调用期间） |
| **同步/异步标记** | 见下表 | 区分消息类型 |

**消息类型（必辨）**：

| 类型 | 符号 | 语义 |
|------|------|------|
| **同步消息** | `────▶`（实线 + **实心三角**箭头） | 调用方**等待**返回后才继续（阻塞），最常见的普通方法调用 |
| **异步消息** | `────▷`（实线 + **开放/空心**箭头） | 调用方**不等**返回，发完就继续（如发送消息队列、事件通知） |
| **返回消息** | `┈┈┈◀`（虚线 + 开放箭头） | 把结果返回给调用方（可选，通常省略以保持图面简洁） |

**完整示例（用户登录的顺序图）**：

```text
  用户              :LoginUI             :LoginCtrl           :UserDB
    │                   │                    │                   │  ← 对象（实例）在顶端，生命线向下
    │  输入账号、密码     │                    │                   │
    │──────────────────▶│                    │                   │  ← 同步消息（实心三角箭头）
    │                   ▓▓ 激活条 ▓▓          │                   │     LoginUI 正在执行
    │                   │ login(id,pwd)      │                   │
    │                   │───────────────────▶│                   │
    │                   │                    ▓▓ 激活条 ▓▓          │
    │                   │                    │ findUser(id)      │
    │                   │                    │──────────────────▶│
    │                   │                    │                   │
    │                   │                    │      User 对象     │
    │                   │                    │◀──────────────────│  ← 返回消息（虚线）
    │                   │     boolean ok     │                   │
    │                   │◀───────────────────│                   │
    │   显示登录结果      │                    │                   │
    │◀──────────────────│                    │                   │
    │                   │                    │                   │
    ← 时间自上而下增长（消息越靠上越早发生）─────────────────────────▶
```

**画图/读图要点**：
- **时间从上到下**，消息越靠上越早发生。
- **对象在顶端**，顺序图只有对象（实例），**没有类**——这是与类图最直观的区别。
- 若一个对象在交互中途被销毁，在生命线终点画一个大叉 `✕`。
- **填空技巧**：顺序图中的**消息名**通常就是类图里被调类的**方法名**（含参数），所以"看顺序图填消息"要从对应类的方法里找。

## 五、状态图（2021 上半年上午 41–43 刚考过）

状态图（State Diagram / 状态机图）描述**一个对象在其生命周期中经历的状态、状态间的转换以及触发转换的事件**——回答"这个对象什么时候处于什么状态、什么条件让它变"。

### 5.1 五个基本元素

| 元素 | 符号 | 说明 |
|------|------|------|
| **状态 State** | **圆角矩形** | 对象的一种稳定情形（如"待支付"）。内部可写 `entry/动作`、`do/活动`、`exit/动作` |
| **初始状态** | **实心小圆** `●` | 起点，每个状态图**只有一个** |
| **终止状态** | **牛眼** `◉`（实心圆外套圆圈） | 终点，可以有**零个或多个** |
| **转换 Transition** | 箭头 `────▶` | 从一个状态到另一个状态 |
| **事件 Event / 监护条件 Guard / 动作 Action** | 写在转换箭头上：`事件[监护条件]/动作` | 触发条件；如 `提交订单[库存充足]/生成订单号` |

**事件的四种类型**（选择题考点）：
1. **调用事件**：收到一个方法调用（如 `start()`）。
2. **信号事件**：收到一个异步信号/消息。
3. **变化事件**：`when(布尔表达式)`——**条件为真时触发**（如 `when(余额<0)`）。注意：`when(...)` 是**变化事件**，不是时间事件。
4. **时间事件**：`after(时长)`——**经过指定时间后触发**（如 `after(10s)`）。

> **2021 上半年卷 43 题的坑**：`when(b=5)` 是**变化事件**（条件成立时触发），**不是时间事件**；而"**状态由事件触发**"这种说法本身是错的——**事件触发的是"状态转换（迁移）"，不是状态本身**（状态是被"进入/退出"的，不是被"触发"的）。这个辨析点会重复考。

### 5.2 组合状态与历史状态（进阶，大题可能考）

- **组合状态（Composite/嵌套状态）**：一个状态内部又含若干子状态（子状态机）。2021 上半年卷 42 题的"组合状态 C 内含子状态 A、B"就是它——**从组合状态 C 到 D 的转换，触发条件是"C 内部子状态 A、B 的所有动作都执行完"**（不能只等其中一个）。
- **历史状态（History State）**：用带 `H` 的圆圈表示。记录组合状态**离开时**所处的子状态，重新进入组合状态时**从上次离开的地方继续**，而不是从头开始。

**完整示例（订单对象的状态图）**：

```text
      ● (初始状态，唯一)
      │
      ▼
  ╭──────────╮  提交订单/生成订单  ╭──────────╮  付款成功/通知发货  ╭──────────╮
  │  待支付    │───────────────────▶│  待发货    │───────────────────▶│  已发货    │
  ╰────┬─────╯                    ╰────┬─────╯                    ╰────┬─────╯
       │ 取消订单/退款                  │ 取消订单/退款                  │ 确认收货/完成订单
       │                               │                               │
       │                               ▼                               ▼
       │                          ╭──────────╮                   ╭──────────╮
       │                          │   已取消    │                   │   已完成    │
       │                          ╰────┬─────╯                   ╰────┬─────╯
       │                               │                               │
       ╰───────────────────────────────┼───────────────────────────────┤
                                         ▼                             ▼
                                      ◉ (终止)                      ◉ (终止)
```

> 注意：本题里"已取消"和"已完成"都是终止状态（牛眼），所以图里有**两个**终止状态，这是合法的（终止状态可以有零个或多个，初始状态只能有一个）。

## 六、活动图（行为流程，与流程图最像）

活动图描述**系统的工作流程**——从一项活动到另一项活动的控制流，可描述**并发**行为。

### 6.1 基本元素

| 元素 | 符号 | 说明 |
|------|------|------|
| **活动 Action/Activity** | **圆角矩形** | 一项可执行的工作（注意与状态图**也是圆角矩形**，但活动图里装的是"做"，状态图里装的是"是"） |
| **起点** | 实心小圆 `●` | 唯一 |
| **终点** | 牛眼 `◉` | 可有多个 |
| **判定 Decision** | **菱形** `◇` | 条件分支（相当于 if） |
| **合并 Merge** | **菱形** `◇` | 多条支路汇合（与判定同符号，但只有汇合、无条件） |
| **分叉 Fork** | **粗横线**（同步条） | **一条控制流拆成多条并发的控制流**（"一变多"） |
| **汇合 Join** | **粗横线**（同步条） | **多条并发控制流全部到达后才继续**（"多合一"，等齐了才走） |
| **泳道 Swimlane** | 纵向分区 | 把活动按**角色/对象**分组，回答"这件事谁来做" |

**完整示例（网购下单的活动图，含分叉/汇合）**：

```text
        ● (起点)
        │
  ╭─────▼─────╮
  │   提交订单  │
  ╰─────┬─────╯
        ▼
      ◇ 库存充足？───否──▶╭──────────╮
        │ 是                │  提示缺货  │──────────╮
        ▼                  ╰──────────╯          │
  ╭─────┴─────╮                                  │
  │   支付货款  │                                  │
  ╰─────┬─────╯                                  │
        ▼                                        │
      ◇ 支付成功？───否──▶╭──────────╮           │
        │ 是                │  重新支付  │──────────┤
        ▼                  ╰──────────╯          │
  ═══════════ fork（分叉：一条控制流拆成两条并发的控制流）
  ╭──────────────╮        ╭──────────────╮        │
  │  生成物流单    │        │   通知客户     │        │
  ╰──────┬───────╯        ╰──────┬───────╯        │
         │                       │                 │
  ═══════════ join（汇合：两条并发流全部到齐后才继续）
         │                                         │
  ╭─────▼─────╮                                    │
  │   完成订单  │◀───────────────────────────────────╯
  ╰─────┬─────╯
        ▼
       ◉ (终点)
```

> **读图检查**：两个菱形都是**判定**（库存充足？/ 支付成功？）；两条粗横线分别是 **fork（分叉）** 与 **join（汇合）**——这是活动图与流程图最本质的区别（**流程图画不出并发**）。

### 6.2 活动图 vs 流程图（常考辨析）

| 维度 | 活动图（UML） | 流程图（传统） |
|------|--------------|---------------|
| **能否表示并发** | **能**（fork/join 粗横线表示并行执行） | **不能**（流程图本质上是单线的顺序/分支/循环） |
| **泳道** | **有**（按角色分区） | 一般无 |
| **对象流** | 可带（活动旁可连接对象及其状态） | 无 |
| **用途** | 面向对象分析设计中的**业务流程/用例内部流程**建模 | 传统软件设计的**算法/程序流程**描述 |
| **基本节点** | 活动（圆角矩形） | 处理框（矩形）、判断框（菱形） |

> **一句话区别**：**活动图 = 面向对象版、支持并发的流程图**。题目问"活动图与流程图的主要区别"——答**活动图能描述并发（分叉/汇合）与泳道**。

### 7.2 试题三的 4 种常考问法

| 问法 | 题型 | 应对 |
|------|------|------|
| **① 图形填空**：给一张类图/用例图/顺序图，挖掉类名、属性名、方法名、关系线上的多重性或 `《include》/《extend》` 字样 | 最高频，约占 8–12 分 | 见 §7.3 套路 |
| **② 判断关系类型**：问"X 与 Y 之间是什么关系（关联/聚合/组合/泛化/实现/依赖）" | 每年必考 2–4 空 | 用 §2.2 的**代码级判别**和关键词法 |
| **③ 解释含义**：简答"图中类 A 与类 B 之间的菱形符号表示什么含义" | 偶尔出现 | 按"整体-部分 + 部分能否独立存在"作答 |
| **④ 用例图/顺序图联动**：给用例图填顺序图的消息，或给状态图填状态名与事件 | 近年增多 | 消息名从类图方法名里找；状态名从需求文字的"状态词"里找 |

### 7.3 答题套路（6 步，直接照做）

1. **先读题不看图**：把需求描述里的**名词**圈出来（→ 候选类/属性），**动词**圈出来（→ 方法/用例/消息）。
2. **区分"类 vs 属性"**：**能独立存在且有身份的名词是类**（如"读者"）；**只依附于某对象、无独立操作的名词是属性**（如"姓名""学号"）。
3. **用关键词判关系**（直接抄表）：
   - "**由……构成 / 与……同生共死 / 整体销毁部分也不存在**" → **组合**（◆◆）
   - "**拥有 / 包含……，部分可独立使用/共享**" → **聚合**（◆）
   - "**是……的一种 / 分为 A 类、B 类**" → **泛化**（△，实线）
   - "**实现 / 遵循……接口 / 支持某操作**" → **实现**（△，虚线）
   - "**每次都要 / 公共步骤 / 先做 X 再做 Y**" → 用例的 **include**
   - "**如果 / 可以 / 可选 / 在……条件下**" → 用例的 **extend**
   - "**使用 / 调用，传进来用**" → **依赖**（虚线箭头）
   - 其余长期联系 → **关联**（实线）
4. **多重性从数量词读**："一个读者可借**多本**书" → 读者端 `1`，图书端 `*`；"一个订单**只属于**一个客户" → 订单端 `*`，客户端 `1`。
5. **顺序图消息 = 类方法**：填空时数一数缺几条消息，到对应类的方法列表里**按顺序**认领；参数从需求文字抄。
6. **回填后自洽检查**：把填完的图当"说明书"重读一遍需求，看能否跑通；若某条关系导致"部分能脱离整体"，就该是聚合不是组合。

### 7.4 上午 UML 题的保分点（科目一也考）

| 考点 | 保分结论 |
|------|---------|
| 每种图"展现什么" | 类图=静态结构；对象图=**某一时刻**对象及关系的快照；顺序图=按**时间**组织的交互；状态图=**反应型对象**（由外部事件驱动、在有限状态间转换的对象）的状态变迁 |
| 状态由事件触发？ | ❌ 错。**事件触发的是"转换（迁移）"，不是状态本身**（2021 上半年 43 题） |
| `when(b=5)` 是什么事件 | **变化事件**（条件为真时触发），不是时间事件；`after(5s)` 才是时间事件 |
| 关系强弱排序 | 依赖 < 关联 < 聚合 < 组合 < 泛化 = 实现 |
| 抽象类能否实例化 | ❌ 不能。抽象类（类名斜体）**没有自己的直接对象**，只能通过子类产生对象（2020 下半年 41 题考过） |
| 活动图 vs 流程图 | 活动图**支持并发（fork/join）与泳道**，流程图不支持 |

## 八、一页纸速记（考前扫这一页）

1. **UML 13 图 = 结构图（静态）+ 行为图（动态）**；下午大题高频 5 种：**类图、用例图、顺序图、状态图、活动图**。
2. **可见性**：`+` public、`-` private、`#` protected、`~` package；**抽象类名斜体**、接口标 `<<interface>>`。
3. **类间六关系（依关聚组泛实）**：
   - **依赖** = 虚线箭头，方法参数/局部变量，用一下；
   - **关联** = 实线箭头，成员变量，长期联系；
   - **聚合** = **空心菱形**在整体端，部分**可独立**（外部注入）；
   - **组合** = **实心菱形**在整体端，部分**同生共死**（内部 new）；
   - **泛化** = 实线**空心三角**指向父类（is-a）；
   - **实现** = 虚线**空心三角**指向接口（implements）。
4. **菱形永远在整体一端，三角永远指向更一般的一端**。
5. **include**：基用例 → 被包含用例，**必执行**；**extend**：扩展用例 → 基用例，**可选**；箭头方向相反。口诀："包含必执行，箭头朝小；扩展可选，箭头朝大。"
6. **用例图三要素**：参与者（框外小人）、用例（椭圆，动宾命名）、系统边界（矩形）；Actor 与用例之间**只能**是关联。
7. **顺序图**：生命线（竖虚线）+ 消息（水平箭头，**同步实心三角/异步开放箭头/返回虚线**）+ 激活条；**只有对象，没有类**；消息名 = 类的方法名。
8. **状态图**：状态（圆角矩形）+ 转换（`事件[条件]/动作`）；初始状态●唯一、终止状态◉可多个；**`when()` = 变化事件，`after()` = 时间事件**；**事件触发的是转换不是状态**。
9. **组合状态**：从组合状态出去，要等**内部所有子状态动作执行完**；**历史状态 H** 可记住上次离开的子状态。
10. **活动图**：活动（圆角矩形）+ 判定/合并（菱形）+ **分叉/汇合（粗横线，表示并发）**+ 泳道；**与流程图的区别 = 支持并发与泳道**。
11. **下午结构**：试题一 DFD、试题二 E-R/数据库、**试题三 UML（15 分，几乎必考）**、试题四 算法（C 语言）、试题五/六 C++/Java 设计模式（二选一）；**4 必答 + 1 选答，每题 15 分，满分 75，合格 45**。
12. **填空三招**：名词找类、动词找方法/用例、关键词判关系（"同生共死→组合、可独立→聚合、是一种→泛化、用一下→依赖"）。
