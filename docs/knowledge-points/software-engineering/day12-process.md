## 一、软件生命周期

### 1.1 三个时期与若干阶段

软件生命周期（Software Life Cycle）是软件从**产生**到**废弃**的整个过程。GB/T 8566（软件生存周期过程）把过程细分为很多类，但**软考常考的经典划分**是把生命周期分为三大时期：

```
┌──────────────────────────────────────────────────────────────────────────┐
│  软件定义期（What to do）  │   软件开发期（How to do）   │  软件运行/维护期 │
├──────────────────────────────────────────────────────────────────────────┤
│  问题定义                  │  概要设计（总体设计）        │  运行            │
│  可行性研究                │  详细设计                   │  维护            │
│  需求分析                  │  编码（实现）               │  （废弃/退役）   │
│                            │  测试                       │                  │
└──────────────────────────────────────────────────────────────────────────┘
```

经典瀑布模型把上述过程串成一条线：

```
问题定义 → 可行性研究 → 需求分析 → 概要设计 → 详细设计 → 编码 → 测试 → 运行维护
```

### 1.2 各阶段的任务与交付物（必背）

| 阶段 | 核心任务 | 关键交付物 | 常考陷阱 |
|------|---------|-----------|---------|
| **问题定义** | 弄清"要解决的是什么问题" | 问题定义报告（规模/目标） | 不是"怎么做"，是"做什么" |
| **可行性研究** | 用最小代价在最短时间内确定问题**是否值得解决、能否解决** | 可行性研究报告 | 经济/技术/法律/操作**四类**可行性；成本-效益分析 |
| **需求分析** | 明确目标系统"必须做什么" | **需求规格说明书（SRS）** | SRS 是用户与开发方的**基线/合同** |
| **概要设计** | 划分模块、确定模块间接口与体系结构 | 概要设计说明书（结构图） | 不写算法细节 |
| **详细设计** | 设计每个模块的内部算法与数据结构 | 详细设计说明书（流程图/伪代码） | 不是"编码" |
| **编码** | 把详细设计翻译成程序 | 源程序 | 语言选择在概要设计阶段就应确定 |
| **测试** | 发现并纠正错误 | 测试计划、测试用例、测试报告 | 单元→集成→系统→验收 |
| **运行维护** | 保证系统持续可用 | 维护记录 | **维护是生命周期中时间最长、花费最大的阶段** |

> ⚠️ **易错点**：概要设计确定模块结构，详细设计确定模块算法；"确定用什么编程语言"属于**概要设计**（更准确地说是概要设计/计划阶段的技术选型）而不是编码阶段。

### 1.3 可行性研究的四类内容

| 类型 | 回答的问题 | 典型手段 |
|------|-----------|---------|
| **经济可行性** | 值得做吗？投入产出比？ | **成本-效益分析**（投资回收期、净现值） |
| **技术可行性** | 做得了吗？技术/资源够吗？ | 技术风险评估、原型验证 |
| **法律可行性** | 合法吗？侵权/合同/知识产权？ | 专利/许可调查 |
| **操作可行性**（用户可行性） | 用户用得起来吗？流程跑得通吗？ | 用户访谈、业务流程分析 |

> **记忆口诀**：**"钱、技、法、人"** —— 经济（钱）、技术（技）、法律（法）、操作（人）。

### 1.4 软件维护的四种类型（生命周期末端的必考点）

| 维护类型 | 目的 | 占比（经验值） |
|---------|------|---------------|
| **改正性维护（纠错性）** | 改正交付后发现的错误 | ~20% |
| **适应性维护** | 适应**环境变化**（OS/硬件/业务规则改变） | ~25% |
| **完善性维护** | 增加新功能、改进性能、提升体验 | **~50%（最大头）** |
| **预防性维护** | 主动改进以提高**可维护性**、防患于未然 | ~5% |

> ⚠️ **易错点**：题目说"用户提出增加一个报表功能"→**完善性**维护（不是适应性）；"操作系统升级后系统不能运行"→**适应性**维护（不是改正性——交付时本就是对的）。

## 二、软件过程模型（必考核心）

### 2.1 瀑布模型（Waterfall）

**起源**：W. W. Royce，1970 年《Managing the Development of Large Software Systems》。

> ⚠️ **历史真相（冷知识，偶考）**：Royce 原始论文描述的其实是**带反馈回溯**的模型；"严格顺序、不可回溯"的瀑布是后人简化的产物。考题一般按"经典瀑布 = 线性顺序 + 文档驱动"作答。

```
问题定义 → 可行性研究 → 需求分析 → 概要设计 → 详细设计 → 编码 → 测试 → 运行维护
   │          │            │           │          │        │       │
   ▼          ▼            ▼           ▼          ▼        ▼       ▼
  文档       文档         SRS        概设书      详设书     代码   测试报告
   （每个阶段结束有"里程碑评审"，通过后才进入下一阶段）
```

- **核心特征**：**线性顺序**、**文档驱动**（每阶段有明确的文档交付物）、**阶段评审**（里程碑）。
- **优点**：过程清晰、便于管理与分工、里程碑明确、文档完整（便于后期维护与人员交接）。
- **缺点**：要求**需求必须明确且稳定**；错误积累到后期才暴露（"错误放大"）；用户很晚才见到可运行产品；灵活性差、风险后移。
- **适用场景**：需求明确且稳定、技术成熟、对文档要求高的大型项目（军工、航天、金融核心系统）。

### 2.2 V 模型（V-Model）

瀑布模型的变体，把**测试活动**与**开发活动**一一对应，形成 V 字形。

```
  需求分析 ────────────────────────────────┐ 验收测试
      ↓                                    ↑  （用户参与，确认"做的是用户要的吗"）
  概要设计 ──────────────────────┐ 系统测试  ↑
      ↓                          ↑（验证"整体组装后功能对吗"）
  详细设计 ──────────┐ 集成测试  ↑
      ↓               ↑（验证"模块接口对吗"）
    编码 ──→ 单元测试 ↑（验证"模块内部逻辑对吗"）
```

| 开发阶段（左侧） | 对应测试阶段（右侧） | 测试关注 |
|-----------------|---------------------|---------|
| **需求分析** | **验收测试** | 是否满足用户需求 |
| **概要设计** | **系统测试** | 系统整体功能/性能 |
| **详细设计** | **集成测试** | 模块间接口与协作 |
| **编码** | **单元测试** | 模块内部逻辑 |

- **核心特征**：**开发与测试一一对应**、测试活动**提前规划**（每完成一个开发文档即可设计对应测试用例）。
- **优点**：质量保障意识前置、测试有据可依、里程碑清晰。
- **缺点**：与瀑布同样要求**需求明确**、灵活性差；**仍然是顺序模型**，不解决需求变化问题。
- **适用场景**：需求明确、质量/安全要求极高（医疗、汽车电子、金融）。

> ⚠️ **必背对应关系**：需求↔验收、概设↔系统、详设↔集成、编码↔单元。题目常把"概要设计对应集成测试"设为干扰项——**概要设计对应系统测试**。

### 2.3 增量模型（Incremental）

把系统按**功能优先级**分解成若干**增量构件**，**每个增量都是一个可运行的半成品**，逐个开发并交付。

```
第 1 增量（核心功能）──→ 交付 1（用户可用的"骨架"）
      ↓ 追加
第 2 增量（更多功能）──→ 交付 2
      ↓ 追加
第 3 增量（完善功能）──→ 交付 3（最终系统）
```

- **核心特征**：**分批构造、逐批交付**，每个增量实现一部分功能；优先级高的先做。
- **优点**：**早交付早收益**（用户最快用到核心功能）；风险分散到各增量；前期投资少；可从早期增量的使用中获取反馈。
- **缺点**：要求**开放式体系结构**（构件必须能无缝集成）；增量划分困难；**管理复杂**（易退化为"边做边改/代码堆砌"）。
- **适用场景**：需求可分优先级、需要快速交付核心功能、资金分批投入、市场机会窗口紧的项目。

### 2.4 原型模型（Prototype）

构造一个**可快速运行的系统雏形**，让用户**试用并反馈**，借此**澄清与挖掘真实需求**。

```
初始需求 ──→ 快速构造原型 ──→ 用户试用/评价 ──→ ┬─→ 需求明确 ──→ 丢弃原型 ──→ 正式开发
                                                └─→ 需求不明确 ──→ 修改原型（循环）
```

**两种必须区分的变种**：

| 变种 | 做法 | 原型命运 |
|------|------|---------|
| **抛弃型原型**（探索型/实验型） | 快速搭建仅用于**明确需求**，不追求质量 | **用完即弃**，正式系统重新开发 |
| **演化型原型**（演进型） | 原型逐步**演化为最终产品** | **保留并迭代**成交付系统 |

- **核心特征**：**快速构造 + 用户反馈 + 迭代细化需求**。
- **优点**：需求获取快、减少"开发人员以为的用户需求"与真实需求的偏差；用户参与度高、满意度高；适合界面驱动的系统。
- **缺点**：原型可能被**当作产品**硬上线（质量/文档不足）；开发人员易陷入"无止境打补丁"；**文档常被忽略**。
- **适用场景**：需求模糊、需求频繁变化、交互界面占主导、小型系统或新技术探索。

### 2.5 螺旋模型（Spiral）

**起源**：Barry Boehm，1988 年《A Spiral Model of Software Development and Enhancement》（IEEE Computer）。

**把瀑布与原型结合，并在每次迭代中加入风险分析**，沿螺旋线一圈圈推进，**每圈都完成一次"四个象限"的活动**：

```
               ┌───────────────────────────────┐
               │  ① 制定计划                    │
               │  （目标 / 替代方案 / 约束）      │
               │                               │
   ┌───────────┘                               └───────────┐
   │ ④ 客户评估                                   ② 风险分析 │
   │ （评价成果、                                  （评估替代、 │
   │   规划下一圈）      ←──── 螺旋一圈 ────→       识别并化解 │
   │                                              风险、原型）│
   └───────────┐                               ┌───────────┘
               │  ③ 实施工程                    │
               │  （开发与验证本圈的产品）         │
               └───────────────────────────────┘
```

四个活动（每圈循环一次，**必背顺序**）：
1. **制定计划**：确定目标、替代方案与约束。
2. **风险分析**：评估备选方案、**识别风险并采取手段化解**（常通过构造原型降低风险）。
3. **实施工程**：开发并验证本圈交付物。
4. **客户评估**：客户评价成果、规划下一圈。

- **核心特征**：**风险驱动**（这是它与"迭代的原型模型"最本质的区别！）、迭代 + 原型 + 瀑布的融合。
- **优点**：风险**早发现、早解决**（成本低）；灵活、适应需求不完全明确的大项目。
- **缺点**：**风险分析本身成本高**，需要经验丰富的领域专家；管理复杂；难以像瀑布那样定义清晰的中间交付物与验收标准（契约困难）。
- **适用场景**：**规模大、复杂、高风险**、需求不完全明确的项目（大型企业系统、新产品研发）。

> ⚠️ **最高频易错点**：**螺旋模型 = 风险驱动**。只要题干出现"风险分析/风险驱动/ Boehm"，首先想到螺旋模型。它不是"原型驱动"，也不是简单的"迭代模型"。

### 2.6 敏捷开发与 Scrum

**起源**：2001 年 2 月，17 位软件先驱在美国犹他州雪鸟（Snowbird）签署《**敏捷软件开发宣言**》。

**敏捷四条价值观**（必背，注意是"**高于**"而非"否定"）：

| 敏捷认为更重要 | 相较于（次要但仍有价值） |
|---------------|------------------------|
| **个体和互动** | 流程和工具 |
| **可工作的软件** | 详尽的文档 |
| **客户合作** | 合同谈判 |
| **响应变化** | 遵循计划 |

> ⚠️ 右项并非无价值，敏捷只是认为**左项更应被优先对待**。题目若说"敏捷完全不需要文档/计划"——**错**。

**Scrum 框架（3-3-5）**：

| 类别 | 内容 |
|------|------|
| **3 个角色** | 产品负责人（Product Owner，管理产品待办列表优先级）、Scrum 教练（Scrum Master，服务团队、消除障碍、推进流程）、开发团队（自组织、跨职能） |
| **3 个工件** | 产品待办列表（Product Backlog，全部需求的有序清单）、迭代待办列表（Sprint Backlog，本 Sprint 要做的）、产品增量（Increment，可用的累积成果） |
| **5 个事件** | Sprint（迭代，**周期通常 2–4 周**）、Sprint 计划会议、每日站会（Daily Scrum，**15 分钟**，三个问题：昨天做了什么/今天做什么/有什么障碍）、Sprint 评审会议、Sprint 回顾会议 |

- **核心特征**：**小步快跑、迭代增量、拥抱变化、客户全程参与、文档从简**。
- **优点**：快速响应需求变化；快速交付可用软件；沟通成本低、客户满意度高。
- **缺点**：**文档不足**不利于后期维护与交接；对团队素质与自组织能力要求高；**大规模（大团队、长周期项目）协调困难**。
- **适用场景**：需求变化频繁、中小型团队、互联网/面向用户的产品。

### 2.7 【必考】六大过程模型对比表

> 这张表是**科目一的高频考点**，建议整表背诵，重点记每个模型的**唯一识别词**。

| 模型 | 提出者/年代 | 核心特征（**识别词**） | 驱动方式 | 优点 | 缺点 | 适用场景 |
|------|-----------|----------------------|---------|------|------|---------|
| **瀑布** | Royce, 1970 | 线性顺序、**文档驱动**、阶段评审 | 文档/里程碑 | 过程清晰、易管理、文档完整 | 需求须明确、错误积累晚发现、用户见产品晚、风险后移 | 需求明确稳定、技术成熟的大型项目 |
| **V 模型** | — | 开发与**测试一一对应** | 测试/质量 | 测试提前规划、质量有保障 | 同瀑布：需求须明确、灵活性差 | 需求明确、质量/安全要求极高 |
| **增量** | — | **分批构造、逐批交付**可运行构件 | 交付/优先级 | 早交付早收益、风险分散、投资分批 | 需开放式体系结构、增量划分难、易退化为"边做边改" | 需求可分优先级、需快速交付核心功能 |
| **原型** | — | **快速构造 + 用户反馈**澄清需求 | 需求/反馈 | 需求获取快、偏差小、用户参与度高 | 原型可能被当作产品、文档易缺失、易打补丁 | 需求模糊、界面主导、小型系统 |
| **螺旋** | **Boehm, 1988** | **迭代 + 风险分析**、四象限循环 | **风险** | 风险早发现早化解、灵活适应大项目 | 风险分析成本高、需专家、管理与契约困难 | **大型、复杂、高风险**、需求不完全明确 |
| **敏捷 Scrum** | 2001 宣言 | **小步快跑、拥抱变化**、迭代增量 | 变化/价值 | 响应变化快、交付快、客户参与 | 文档不足、依赖团队素质、大规模协调难 | 需求变化频繁、中小型团队、互联网产品 |

**补充速览（偶考）**：

| 模型 | 一句话特征 |
|------|-----------|
| **喷泉模型** | **面向对象**开发模型，迭代、**无间隙**（各阶段重叠、无明确边界） |
| **RUP（统一过程）** | 用例驱动、以架构为中心、**迭代增量**；四大阶段：初始/细化/构造/移交 |
| **构件复用模型** | 利用可复用构件组装，强调**软件复用** |

### 2.8 易混点辨析（四组，必看）

**① 螺旋 vs 原型 vs 迭代——"谁驱动"？**

| 问法 | 答案 |
|------|------|
| "以**风险**驱动/每次迭代都做**风险分析**" | **螺旋模型** |
| "构造**原型**以**明确需求**，原型用完即弃" | **抛弃型原型模型** |
| "原型**逐步演化**为最终产品" | **演化型原型模型** |
| "把系统分成**多个可运行增量**分批交付" | **增量模型** |

> 螺旋模型**也用原型**，但它用原型是**手段**（在"风险分析"象限中降低风险），**目的**是风险控制。题目若强调"每一圈都包含风险分析与原型验证"，答螺旋。

**② 增量 vs 原型——"交付的是产品还是需求验证"？**

```
增量模型：每个增量 = 可运行的产品的一部分 ──→ 最终累积成完整系统（产物保留）
原型模型：原型     = 需求的"试验田"        ──→ 抛弃型用完即弃（产物不保留）
```
> 一句话区分：**"增量交产品，原型定需求"**。增量模型关心的是**分批交付**；原型模型关心的是**把需求问清楚**。

**③ V 模型的四对对应关系（易错）**

```
需求分析 ↔ 验收测试      （易错点：不是"系统测试"）
概要设计 ↔ 系统测试      （易错点：不是"集成测试"）
详细设计 ↔ 集成测试      （易错点：不是"单元测试"）
编  码   ↔ 单元测试
```
> 记忆链：**越靠左的开发文档对应越靠右的测试阶段**——需求是最早的文档，对应最晚的验收测试；详细设计比概要设计更细，对应更底层的集成测试。

**④ 敏捷不等于"无文档无计划"**

敏捷四价值观的右项（流程工具、文档、合同、计划）**仍需存在**，只是优先级更低。Scrum 的 Sprint Backlog 本身就是一种轻量级计划。

## 三、需求分析

### 3.1 需求工程 vs 需求分析

```
需求工程（Requirement Engineering）
   ├── 需求开发（本日重点）
   │     ├── 需求获取
   │     ├── 需求分析
   │     ├── 需求规约（写 SRS）
   │     └── 需求验证（评审）
   └── 需求管理
         ├── 需求基线
         ├── 需求变更控制
         ├── 需求跟踪
         └── 需求状态管理
```

> ⚠️ **需求分析**只是需求开发中的一个环节；**需求工程**范围更大，还包含需求管理。题目问"需求分析阶段的主要任务"时不要答"变更控制"。

### 3.2 需求的分类（必考）

```
软件需求
   ├── 功能需求     ：系统必须提供/完成的功能（"做什么"）
   ├── 非功能需求   ：性能、可靠性、可用性、安全性、可维护性、可移植性等（"做得多好"）
   └── 设计约束     ：必须遵守的技术/标准/平台/语言/法规限制（"被限制成什么样"）
```

| 类别 | 判断标志 | 例子 |
|------|---------|------|
| **功能需求** | 描述"系统提供什么功能/服务" | "用户可以查询图书借阅记录" |
| **非功能需求** | 描述**质量属性或性能指标** | "查询响应时间 ≤ 2 秒""系统可用性 ≥ 99.9%""支持 500 并发" |
| **设计约束** | 描述**必须遵守的限制** | "必须用 Java 开发""必须运行在国产化平台上""符合等保 2.0" |

> ⚠️ **易错点**：**"性能需求属于非功能需求"**，不是"功能需求"。题目常把"系统每秒处理 100 笔交易"混在功能需求里。

也有人按抽象层次分为：**业务需求**（组织为什么做）→ **用户需求**（用户用它完成什么）→ **系统需求**（系统具体要做什么，含功能/非功能）。

### 3.3 需求获取（Elicitation）

常用方法（多选/判断题常考）：

| 方法 | 特点 | 适用 |
|------|------|------|
| **访谈** | 一对一/一对多，深入但耗时 | 需求清晰、干系人少 |
| **观察（现场跟岗）** | 看真实工作流程，发现"说不出来的隐性需求" | 业务流程复杂、用户说不清 |
| **问卷调查** | 覆盖面广、可量化，但难深入 | 用户群体大、需求浅 |
| **会议（JAD 联合应用开发）** | 干系人集中开会、快速达成共识 | 干系人多、需对齐 |
| **原型法** | 用原型激发反馈 | 需求模糊、界面驱动 |
| **用例分析** | 用用例图描述交互场景 | 面向对象分析（OOA） |

> 口诀：**"问、看、查、开、做（原型）、演（用例）"**。

### 3.4 需求规约（SRS）

**需求规格说明书（Software Requirement Specification, SRS）** 是需求分析阶段的**核心交付物**。

**IEEE 830 定义的 SRS 应具备的性质**（必背）：

| 性质 | 含义 |
|------|------|
| **正确性** | 准确描述系统行为 |
| **无歧义性** | 每条需求只有一种解释（不能"大概""可能"） |
| **完整性** | 覆盖所有需要的需求 |
| **一致性** | 需求之间不能矛盾 |
| **可验证性** | 每条需求都可通过测试/检查确认 |
| **可修改性** | 结构清晰，便于变更 |
| **可追踪性** | 能追溯到来源（用户需求/合同）并向前关联到设计与测试 |

**SRS 的作用**：
- 用户与开发方之间的**基线/契约**（验收依据）；
- 后续**设计、编码、测试**的依据；
- 项目**度量、计划与成本估算**的基础。

### 3.5 需求验证

在 SRS 交付前确认需求"做对了"：

- **需求评审**（同行评审，正式评审与非正式走查）——最常用；
- **原型验证**（构造可执行原型让用户确认）；
- **形式化验证 / 自动化一致性检查**（用工具检查一致性、完整性）；
- **编写测试用例验证**（提前为每条需求设计验收测试）。

> ⚠️ 需求验证**不是**"运行程序"——此时还没有程序可运行。

## 四、结构化分析方法（SA）

### 4.1 方法概述

**结构化分析（Structured Analysis, SA）** 由 Tom DeMarco 在 1978 年《Structured Analysis and System Specification》中系统化，是**面向数据流**的传统分析方法，也是**软考下午科目二大题的常客**。

**核心思想**：**自顶向下、逐层分解**（分解与抽象）——把复杂系统一层层拆成足够简单的小加工。

**三大工具**：

```
数据流图（DFD）  ── 描述系统功能与数据流向（"做什么"）
数据字典（DD）   ── 严格定义 DFD 中出现的所有数据（"数据是什么"）
加工逻辑（小说明）── 描述底层加工的处理规则（"具体怎么做"）
```

### 4.2 DFD 的四要素（必背）

| 要素 | 符号 | 含义 | 易错点 |
|------|------|------|-------|
| **外部实体** | **矩形/方形** | 系统之外与系统交互的人、设备或外部系统 | 是**数据**的源/宿，不是系统的组成部分 |
| **加工/处理** | **圆角矩形（或圆形）** | 把输入数据变换为输出数据 | 必须有**输入也有输出** |
| **数据流** | **带箭头的线** | 表示数据的流动方向 | DFD 中**只有数据流，没有控制流**！ |
| **数据存储** | **双横线 / 开口矩形** | 数据的静态保存处 | 可以是文件、数据库表 |

> ⚠️ **DFD 与程序流程图的根本区别**：DFD **不表示控制逻辑**（没有判断框、没有循环、没有时序），只表示"数据从哪来、到哪去、被谁加工"。这是**高频考点**。
>
> ⚠️ 一个加工可以有**多个**输入/输出数据流；但**每个数据流必须命名**（命名应为名词/名词短语，反映数据内容）。

### 4.3 DFD 的分层与平衡（核心考点）

```
顶层 DFD（关联图 / Context Diagram）
   └─ 把整个系统看作"一个加工"，只画外部实体与系统之间的数据流
      ↓ 分解
0 层 DFD ── 系统的主要加工
   └─ 分解
1 层 DFD ── 某个加工的细化
   └─ 分解
2 层 DFD …（直到每个加工足够简单、可写出"小说明"为止）
```

**父图与子图的关系**：上层图（父图）中的一个加工，被细化为下层图（子图）中的多个加工。

**平衡规则（必考）**：
1. **数量一致**：子图的**外部数据流**（与外部实体/存储交互的）必须与父图中被分解加工的数据流**一一对应**；
2. **方向一致**：输入/输出方向不能变；
3. **命名一致**：数据流名称应相同（或明显等价）。

> 口诀：**"父图子图要平衡，进出数据不能变"**。

**加工编号规则**：逐层编号，如 1、1.1、1.1.1，便于追溯到父加工。

### 4.4 完整示例：图书馆借阅系统

**需求描述**：
1. **读者**提交**借书请求**，系统查询图书在库情况与读者借阅记录后**登记借阅**，并返回**借书成功**消息。
2. **读者**提交**还书请求**，系统更新图书状态、读取并更新借阅记录，必要时发出**逾期催还**通知。
3. **管理员**提交**新书入库单**，系统将新书信息登记到图书信息表。

**实体与存储识别**：

| 外部实体 | 数据存储 | 说明 |
|---------|---------|------|
| 读者 | D1 图书信息表 | 记录每本图书的在库状态 |
| 管理员 | D2 借阅记录表 | 记录读者的借阅/归还明细 |

**顶层 DFD（关联图）**——整个系统是**一个**加工：

```text
        借书请求、还书请求
┌──────┐                   ┌──────────────────┐
│      │──────────────────►│                  │
│      │                   │                  │
│ 读者 │◄──────────────────│  图书馆借阅系统  │
└──────┘                   └────────┬─────────┘
        借书成功、逾期催还
                                    ▲ 新书入库单
                              ┌────────────┐
                              │   管理员   │
                              └────────────┘
```

**0 层 DFD**——分解为 3 个加工、2 个数据存储：

```text
        借书请求                  登记借阅
┌──────┐        ┌────────────┐                ╔══════════════╗
│      │───────►│            │───────────────►║D2 借阅记录表 ║
│      │        │            │                ╚══════════════╝
│ 读者 │◄───────│ 1 借书处理 │                       │
└──────┘        └──────┴─────┘                       │
        借书成功       ▼ 查询在库                    │ 读取借阅记录
                ╔══════╤═════════╗                   │
                ║ D1 图书信息表  ║◄───────────       ▼
                ╚═══════╧════════╝            ┌──────┬─────┐        ┌──────┐
                        ▲                     │            │还书请求    │      │
                        │                     │            │◄───────│      │
                        │ 入库新书                │ 2 还书处理 │        │ 读者 │
                        │                     └────────────┘───────►└──────┘
         新书入库单     │                                        逾期催还
┌────────────┐      ┌───┬────────┐
│   管理员   │─────►   │ 3 新书入库 │
└────────────┘      └────────────┘
```

**数据流清单与平衡校验**：

| 数据流 | 起点 | 终点 | 备注 |
|--------|------|------|------|
| 借书请求 | 读者 | 加工 1 | 外部流 |
| 借书成功 | 加工 1 | 读者 | 外部流 |
| 还书请求 | 读者 | 加工 2 | 外部流 |
| 逾期催还 | 加工 2 | 读者 | 外部流 |
| 新书入库单 | 管理员 | 加工 3 | 外部流 |
| 查询在库 | D1 | 加工 1 | 内部流（读） |
| 登记借阅 | 加工 1 | D2 | 内部流（写） |
| 读取借阅记录 | D2 | 加工 2 | 内部流（读） |
| 更新图书状态 | 加工 2 | D1 | 内部流（写） |
| 入库新书 | 加工 3 | D1 | 内部流（写） |

> **平衡校验**：0 层图中"加工 1 借书处理"的输入是【借书请求、来自 D1 的查询在库】，输出是【借书成功、写入 D2 的登记借阅】。若把"1 借书处理"进一步细化为 1.1 查询、1.2 登记，则子图的外部流必须是【借书请求（入）、借书成功（出）、查询在库（入）、登记借阅（出）】——**数量与方向完全一致**，这就是父子图平衡。

### 4.5 数据字典（DD）

**作用**：给 DFD 中出现的**所有数据流、数据存储、数据项**下严格定义，弥补 DFD"只画不定义"的不足。DD 与 DFD **共同构成需求规约的核心**。

**四类条目**：数据流条目、数据存储条目、数据项条目、加工条目（底层加工的小说明）。

**常用符号（必背）**：

| 符号 | 含义 | 例子 |
|------|------|------|
| `=` | 等价于 / 定义为 | `借书请求 = 读者证号 + 图书编号` |
| `+` | 与（顺序连接） | `日期 = 年 + 月 + 日` |
| `|` | 或（选择其一） | `支付方式 = 现金 | 支票 | 转账` |
| `{ }` | 重复（迭代） | `借阅清单 = { 图书编号 }`（可重复 0 次或多次） |
| `( )` | 可选（可出现 0 次或 1 次） | `读者 = 证号 + 姓名 + (电话)` |
| `[ ]` | 选择（与 `|` 等价，有时用 `[a|b]`） | `性别 = [男 | 女]` |

**完整示例**：

```
数据流条目：借书请求 = 读者证号 + 图书编号 + 借阅日期
数据项条目：读者证号 = {"R" + 6 位数字}        // 取值范围
数据项条目：借阅日期 = 年 + 月 + 日
数据存储条目：D2 借阅记录表 = { 读者证号 + 图书编号 + 借出日期 + 应还日期 + 状态 }
加工条目：  详见 4.6 小说明
```

### 4.6 加工逻辑（小说明）

**小说明**用于描述**叶子加工**（不再分解的最底层加工）的处理规则。三种常用工具：

| 工具 | 形式 | 特点 | 适用 |
|------|------|------|------|
| **结构化语言**（结构化英语/伪代码） | 顺序 + IF/CASE + 循环 | 介于自然语言与程序之间，易读 | 一般逻辑 |
| **判定表（决策表）** | 条件 × 动作 的**表格** | 能穷举**全部条件组合**，不易遗漏 | 多条件组合决策 |
| **判定树（决策树）** | **树形图** | 直观、易理解、易沟通 | 条件较少时 |

**判定表的四部分**（必背）：

```
┌───────────────────────────────────┐
│ 条件定义（条件桩）                  │  ← 列出所有条件
├───────────────────────────────────┤
│ 条件取值组合（条件项）              │  ← 每一列是一种组合
├───────────────────────────────────┤
│ 动作定义（动作桩）                  │  ← 列出所有可能动作
├───────────────────────────────────┤
│ 动作选择（动作项）                  │  ← 每一列对应组合所选动作
└───────────────────────────────────┘
```

**示例——"借阅审批"判定表**（条件：是否为本馆读者 / 是否有逾期未还 / 在库数量是否足够）：

| | 规则 1 | 规则 2 | 规则 3 | 规则 4 | 规则 5 | 规则 6 |
|---|---|---|---|---|---|---|
| 是本馆读者？ | N | Y | Y | Y | Y | Y |
| 有逾期未还？ | — | N | N | Y | Y | Y |
| 在库数量足够？ | — | Y | N | Y | N | N |
| **允许借阅** |  | ✓ |  | ✓ |  |  |
| **提示无库** |  |  | ✓ |  | ✓ | ✓ |
| **提示先还书** |  |  |  | ✓ | ✓ |  |
| **提示办证** | ✓ |  |  |  |  |  |

> 说明：`—` 表示该条件在该规则下不影响结论（**无关条件**）。判定表的**列数 ≤ 条件数的全组合数**，通过合并无关条件可以化简。

> ⚠️ **易错点**：判定表最适合**条件组合较多、互相牵连**的场景；判定树适合**条件少**、需要给业务人员看的场景。题目若说"某加工有 3 个条件、每个条件 2 种取值，最多需要 **2³ = 8** 列"。

## 五、本日速查与记忆口诀

### 5.1 一页纸结论（建议默写）

1. 软件生命周期三时期：**定义、开发、运行维护**；维护**时间最长、花费最大**。
2. 可行性研究四类：**经济（钱）、技术（技）、法律（法）、操作（人）**。
3. **瀑布 = 文档驱动**；**V = 开发测试对应**；**增量 = 分批交付**；**原型 = 澄清需求**；**螺旋 = 风险驱动**；**敏捷 = 拥抱变化**。
4. **螺旋 = Boehm 1988**；四象限：**计划 → 风险分析 → 实施 → 客户评估**。
5. V 模型对应：**需求↔验收、概设↔系统、详设↔集成、编码↔单元**。
6. 敏捷四价值观：**个体互动 / 可工作软件 / 客户合作 / 响应变化**（均高于右项，但不否定右项）。
7. Scrum：**3 角色 / 3 工件 / 5 事件**；Sprint **2–4 周**；每日站会 **15 分钟**。
8. 需求三分类：**功能 / 非功能（性能在此）/ 设计约束**。
9. SRS 七性质：**正确、无歧义、完整、一致、可验证、可修改、可追踪**。
10. **DFD 四要素 = 外部实体（矩形）+ 加工（圆角矩形）+ 数据流（箭头）+ 数据存储（双横线）**。
11. **DFD 只有数据流、没有控制流**；每个数据流必须命名。
12. **父子图平衡**：子图外部流与父加工数据流**数量、方向、名称一致**。
13. DD 符号：**`= 定义、+ 与、| 或、{ } 重复、( ) 可选`**。
14. 小说明三工具：**结构化语言、判定表、判定树**；判定表四部分：**条件桩、条件项、动作桩、动作项**。
15. 增量 vs 原型：**"增量交产品，原型定需求"**。

### 5.2 高频陷阱清单

| 陷阱 | 正确说法 |
|------|---------|
| "螺旋模型是原型驱动的" | **风险驱动** |
| "V 模型中概要设计对应集成测试" | 概要设计对应**系统测试** |
| "性能需求属于功能需求" | 属于**非功能需求** |
| "敏捷开发不需要文档和计划" | 只是优先级更低，**仍需文档与计划** |
| "演化型原型用完即弃" | **抛弃型**才用完即弃 |
| "DFD 中可以画判断/循环" | DFD **只有数据流，没有控制流** |
| "增加报表功能属于适应性维护" | 属于**完善性维护** |
| "需求分析阶段做变更控制" | 变更控制属于**需求管理**，不是需求开发 |
