🧭 体系定位：面 5 数据库 · 设计理论线——函数依赖/候选码/范式/E-R。上游：0021；下游：0023、下午试题二（回地图）

一、函数依赖（FD）三兄弟

先补两个最基础的人话（没读过上一课也能从这里接上）：

  • 候选码（码） = 能唯一认出一行数据的最小属性组——像学号之于学生表：报一个学号，就能锁定唯一一个学生，而且学号里没有多余的属性。一个表可能有多个候选码（比如身份证号也能），选定其中一个是「主键」。
  • 函数依赖 X→Y 读作「X 决定 Y」——只要知道 X，就能唯一查到一个 Y，像用学号查姓名：学号一样的人姓名必然一样。注意是「唯一确定」，不是「有点关系」。
  • 主属性 = 进了某个候选码的属性；非主属性 = 没进任何候选码的属性。后面 2NF、3NF 的要求全是只对非主属性提的，先记住这对词。
依赖定义例子引发问题
完全依赖必须整个码（如学号+课号）才能决定成绩(学号,课号) → 成绩—（正常情形，不出问题；下面两行才是要消除的毛病）
部分依赖码的一部分就能决定非主属性(学号,课号) → 学生姓名违反 2NF（冗余/异常）
传递依赖A→B、B→C（B 不依赖于 A）学号→系名→系主任违反 3NF

括号里「B 不依赖于 A」是在排除一种情况：传递依赖要求 C 是绕中间商 B 间接够到的——中间的 B 只听 A 的（A→B），C 只听 B 的（B→C），A 得经过 B 才够得着 C。但如果 A 直接就能决定 C（有 A→C），那 C 对 A 就不是「传递」来的，是直接依赖，不构成传递。例：学号→系名→系主任是传递（学号不能直接决定系主任，系名就是中间商）。「排除直接依赖」这个条件有个隐藏前提：要先有「学号→系名」这条直接依赖摆在那里，我们才谈得上检查「它是不是间接来的」。还用这个例子打比方：快递从北京直达上海（学号→系名），那上海就是直接到的；哪怕同时还有一条「北京→济南→上海」的绕路（学号→班长 且 班长→系名），也不能说上海是「经济南中转」来的——因为直达线本来就在。所以判断顺序是：先确认 A→C 直接成立 → 再看中间是否存在 B（A→B、B→C）→ 只有当 C 只能靠 B 绕过去时，才算传递依赖。

二、候选码判定 4 步法（一切范式题的起点）

  1. 把属性按在依赖中出现的位置分类：L（只出现在左部）、R（只在右部）、N（不出现）、LR（两边都有）；
  2. L 和 N 一定在候选码里；R 一定不在（R 类属性能被别人推出来，留着它就多余，不满足候选码的「最小」要求）；
  3. 求 (L∪N) 的属性闭包——闭包就是「这个属性组自己能推出的一堆属性」：从它出发，反复用依赖箭头把新属性拉进来，直到拉不动为止——若已含全部属性，它就是候选码；
  4. 若没含全部，把 LR 属性逐个/组合加入再求闭包，恰好覆盖全属性的即为候选码（可能有多个）。

支线说明：Armstrong 公理三条推规则（考试可能点名，逐个一句话说清，马上出现的手算例题会正好把它们全用到）：①自反律——任何属性组天然能推出自己（知道学号当然就知道学号），这是闭包一开始就包含自己的依据；②传递律——A→B、B→C，则 A→C，像一环扣一环地把新属性拉进群；③增广律——X→Y 成立时，两边加上同样的属性依然成立（学号→姓名成立，则 学号+课号→姓名+课号 也成立），这保证已推出的结论能带着新伙伴继续参与推导。「拉人进群」的求闭包过程，本质就是这三条规则的反复使用。

例：R(A,B,C,D)，F = {A→B, B→C}。分类：A 是 L，D 是 N，B、C 是 R。候选码必含 A、D，把手算过程逐行写出来：

  1. 先有 {A, D}（L 和 N 直接入码）；
  2. {A,D} 里有 A，用 A→B 把 B 拉进来 → {A, D, B}；
  3. 现在有 B 了，用 B→C 把 C 拉进来 → {A, D, B, C}；
  4. 再扫一遍 F = {A→B, B→C}，箭头两端都在里面，没有新属性可拉 → 推不动了，收工。

所以 (AD)⁺ = {A,D,B,C}，覆盖全部属性 → 候选码 AD。所谓「闭包」就是这么一个「拉人进群」的过程。

三、范式：1NF → 2NF → 3NF → BCNF

1NF 属性原子 → 2NF 消除非主属性对码的部分依赖 → 3NF 消除传递依赖 → BCNF 所有决定因素都是候选码

「决定因素」是行话，其实就是依赖箭头左边的那个属性（组）——比如 A→B 里决定因素就是 A。所以 BCNF 这句等价于下面快解第三条「每个函数依赖的左部都是候选码」，两句话说的是一回事。

三条考场快解（原资料口径）：

  • 候选码都是单属性 → 不存在部分依赖 → 至少 2NF；
  • 全部属性都是主属性（都在某候选码里，回忆第一节：主属性=进了候选码的属性）→ 至少 3NF。为什么？因为 2NF、3NF 抓的两种毛病——部分依赖和传递依赖——都只对非主属性判（见下一节例题里的点破段）。表里连一个非主属性都没有，这两种毛病压根没有判的对象，检查自动通过；
  • 每个函数依赖的左部都是候选码 → BCNF。

3NF vs BCNF 分界例（背）：R(A,B,C)，F = {AB→C, C→B}。
先补两行候选码怎么来的：本题 A、B、C 三个属性在依赖里两边都出现，全是 LR 类，没有 L、N 可以直接入码，只能组合着试：
① 试 AB：AB→C 把 C 拉进来，(AB)⁺ = {A,B,C} 覆盖全部 → AB 是候选码；
② 试 AC：里面有 C，用 C→B 把 B 拉进来，(AC)⁺ = {A,C,B} 也覆盖全部 → AC 也是候选码（所以候选码有两个）。
然后 C→B 的左部 C 不是候选码 → 不是 BCNF；但三个属性全进了候选码（都是主属性）→ 仍是 3NF。这里要先点破一个隐藏前提：「传递依赖」这条罪名只对非主属性判（回忆第一节：3NF 的要求全是对非主属性提的）。本题没有非主属性——A、B、C 全是主属性，所以 3NF 根本不检查本题里那对「互相决定」的依赖（AB→C 与 C→B，B 和 C 你推出我、我推出你）；3NF 只问「非主属性有没有被传递依赖牵着走」，本题没有非主属性，罪名自然不成立；而 BCNF 的标准更严——它对所有属性都要求「决定因素必须是候选码」，C→B 的左部 C 不是候选码，所以栽在这一关。结论：3NF 但非 BCNF。

四、E-R 图与模式转换（下午大题铁律）

先说两个词：「关系模式」就是一张具体的表（表名 + 列名那一行）；「外键」就是在一张表里放另一张表的主键，用来指回去——像员工表里存一列「部门编号」，顺着它能查回部门表。

  • E-R 三要素：实体、属性、联系——画在图上：实体 = 矩形框（学生、部门这类要存的东西），属性 = 连在框上的椭圆（学号、姓名），联系 = 连接两个框的菱形（选修、属于），菱形旁标上 1 / N / M。联系类型判定：两个方向各取一端问「最多几个」→ 1:1 / 1:N / M:N。举个 30 字的小例子：问「一个部门最多几名员工？」——多名；再问「一名员工最多属几个部门？」——一个。一头是多、一头是一 → 1:N。两头都多（学生↔课程）是 M:N，两头都一是 1:1。
  • 转换规则：实体 → 一个关系模式；1:1 联系：并入任意一端；1:N 联系：并入 N 端（加对方主键做外键）；M:N 联系：必须独立成一个关系模式，主键 = 双方主键的组合。
⚠ 高频判断 『M:N 联系可以合并进任何一端』——错！只有 1:1 和 1:N 能并入；M:N 独立成表，这是 E-R 大题判分点。

五、自查（先动笔推候选码再点）

自查里有一题考「三类完整性」，正文先补一句人话：实体完整性 = 主键不能空、不能重复（一行都得有个身份证）；参照完整性 = 外键的值必须真的在被参照表里存在（员工表不能填一个不存在的部门编号）；用户定义完整性 = 业务自己定的规则（如 CHECK 年龄>0）。配对记：实体→主键、参照→外键、用户定义→业务规则。（这三类完整性的完整讲解在知识点手册 day07-sql.md，配套课后练习见 day07-sql 之后的 day08-exercises。）

✅ 本课一页收获
  1. 候选码 4 步：L/R/N/LR 分类 → L、N 直接入码 → 求闭包 → LR 补齐。
  2. 范式链：1NF 原子 → 2NF 消部分依赖 → 3NF 消传递依赖 → BCNF 决定因素皆候选码。
  3. 快解：单属性码≥2NF；全主属性≥3NF；左部皆码=BCNF。R(A,B,C) F={AB→C,C→B} → 3NF 非 BCNF。
  4. E-R 转换：1:1 并任一端、1:N 并 N 端、M:N 独立成表（主键 = 双方主键组合）。
